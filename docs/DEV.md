# Development Guide

This file is the repo-local developer guide for the Human Design Transit Display mod. It exists
so that anyone returning to this repo after a break — including the author, who is new to
Minecraft mod development — can run the development loop, understand the JDK requirement, and
know what "verified" means for each phase without re-deriving any of it or re-litigating a
toolchain question that was already settled by observation. Update this file whenever the dev
loop, JDK requirement, or a toolchain finding changes.

## Running the dev client

Run:

```
./gradlew runClient
```

On PowerShell, use `.\gradlew.bat runClient` instead.

This is not a build check — it actually launches Minecraft. Loom compiles the mod, injects it
into a Fabric-loaded Minecraft 1.20.1 instance, and opens a real, playable game window. Its
working directory is this repo's `run/` folder, which is completely separate from the Minecraft
installed by the official launcher (a different `saves/`, `options.txt`, `mods/`, and `logs/`) —
nothing here touches your real `.minecraft` folder.

The `runClient` task does not exit until the game window is closed, so when it is driven by a
tool (rather than a human sitting at the keyboard) it should be started in the background and its
log tailed for readiness, rather than run in the foreground.

A reusable Creative Superflat dev world named `gsd-dev` already exists under `run/saves/gsd-dev`,
created during Phase 1 verification. Reuse this world for manual verification from Phase 2
onward instead of creating a new one each time.

## Running data generation

Run:

```
./gradlew runDatagen
```

Everything under `src/main/generated` is generated output. It is tracked in git (so reviewers and
CI can see what changed), but it is never hand-edited: to change its content, edit the provider in
`src/client/java/transitreport/client/JollyalchemyTransitReportDataGenerator.java` and re-run
`runDatagen` to regenerate the files.

The run currently produces exactly these files:

- `src/main/generated/assets/jollyalchemy-transit-report/blockstates/transit_chart.json` — the
  4-way `FACING` blockstate variants for `TransitChartBlock`, generated by the nested
  `TransitChartModelProvider`.
- `src/main/generated/assets/jollyalchemy-transit-report/models/block/transit_chart.json` — the
  block model, parenting `minecraft:block/orientable` with borrowed furnace textures, also
  generated by `TransitChartModelProvider`.
- `src/main/generated/assets/jollyalchemy-transit-report/models/item/transit_chart.json` — the
  block item's model, generated by the same `TransitChartModelProvider` — specifically by Fabric's
  own auto-item-model mechanism, not by any code written in that provider's `generateItemModels`
  override, which is intentionally left empty (see the finding below).
- `src/main/generated/assets/jollyalchemy-transit-report/lang/en_us.json` — the mod's English
  translation entries, generated by the nested `TransitReportLanguageProvider`.
- `src/main/generated/.cache/` — Minecraft datagen's own internal cache/hash bookkeeping files,
  used to detect stale output between runs. Filenames are content-addressed, so they change
  whenever a provider's registered inputs change; file content also includes a regeneration
  timestamp, so it changes on every run even when the generated content itself does not — that is
  expected and not a sign of drift.

### Phase 2 data-generation findings

Settled by observation while building `TransitChartBlock` and `TransitChartModelProvider`
(RESEARCH.md Assumption A1 and Open Questions 1-2; full detail in
`.planning/phases/02-block-exists-and-places/02-01-SUMMARY.md`):

- **Assumption A1 — confirmed.** Leaving `generateItemModels` empty causes Fabric's model provider
  to auto-generate the block item's model as a plain parent reference to the block model
  (`{"parent": "jollyalchemy-transit-report:block/transit_chart"}`), with zero code required in
  that override.
- **Open Question 1 — confirmed.** `createHorizontallyRotatedBlock` paired with
  `TexturedModel.ORIENTABLE_ONLY_TOP` ran `runDatagen` clean end to end on the first attempt for
  this facing-only, no-`LIT` block — no deviation was needed.
- **Rejected: `createFurnace(Block, TexturedModel.Provider)`.** Hardcodes a
  `BlockStateProperties.LIT` boolean dispatch into the generated blockstate; `TransitChartBlock`
  has no `LIT` property (it extends `HorizontalDirectionalBlock`, not `AbstractFurnaceBlock`), so
  this helper does not match its state definition.
- **Rejected: `TexturedModel.ORIENTABLE`.** Requires a fourth `BOTTOM` texture slot this project
  has no texture for (only front/side/top furnace textures are borrowed); using it would leave the
  block's bottom face pointing at a nonexistent texture.

## JDK requirement

There are two separate JDK questions here, and conflating them is the most common setup mistake
for this generation of Fabric Loom:

- **What the mod compiles to:** Java 17 bytecode (`options.release = 17`, with
  `sourceCompatibility` and `targetCompatibility` both `VERSION_17` in `build.gradle`). This is
  fixed by Minecraft 1.20.1's own runtime requirement and must not change.
- **What runs the Gradle daemon that builds it:** independent of the line above, and only
  required to be JDK 17 or newer.

**JDK 26 is confirmed working end to end for this project.** Phase 1 verification (D-06) treated
"does JDK 26 actually run 1.20.1" as a real, pre-agreed risk — `./gradlew build` succeeding proves
nothing about it, since compiling to Java 17 bytecode never exercises LWJGL natives, Mixin's
bytecode manipulation, or 1.20.1 game code the way `runClient` does. The first `runClient` launch
on JDK 26 completed cleanly: no module access error, no LWJGL native load failure, no Mixin
reflection failure into JDK internals. The pre-agreed Temurin JDK 21 fallback was never triggered
and is not needed for this project.

If a JDK pin ever becomes necessary on a different machine, it belongs in that machine's local,
untracked `%USERPROFILE%/.gradle/gradle.properties` — never in this repository's tracked
`gradle.properties`. This repository has a public GitHub remote, and `.github/workflows/build.yml`
builds on `ubuntu-24.04` with JDK 25: a Windows absolute path in a tracked file would both fail
that build and publish the developer's local Windows username.

## What verified means for Phase 1

Verification passes only when **both** of the following hold, not just the first one:

1. The mod is listed on the in-game Mods screen (via Mod Menu, see the Phase 1 SUMMARY for why a
   dev-only Mods-screen dependency was added) under its display name, "Human Design Transit
   Display".
2. A world is created and actually entered — standing inside a loaded world, not just reaching
   the main menu.

Reaching the main menu is explicitly **not** sufficient. World load is where registries and
mixins are actually exercised; a mod that looks fine at the title screen can still fail the moment
a world loads. Treating "main menu opened" as done would hide exactly the failure mode this
verification step exists to catch.

## Datagen configuration finding

Phase 1 (TOOL-03) settled a disagreement between this project's own research documents:
`STACK.md` §1.4 called `fabricApi { configureDataGeneration { client = true } }` "current,
correct, already working" on the grounds that the build succeeds with it present; `PITFALLS.md`
Pitfall 2 observed that Fabric's own documentation describes `client = true` as a 1.21.4+
addition and expected it to no-op or fail on 1.20.1. Both observations were about
configuration-time acceptance, not runtime effect, so the question was settled by running both
forms and diffing what they actually produce, not by picking a document.

**What was compared:** the datagen-related task list from `./gradlew tasks --all` and the actual
generated output tree from a delete-and-regenerate `./gradlew runDatagen`, once with
`configureDataGeneration { client = true }` present and once with the bare
`configureDataGeneration()` form.

**What was observed:**

- The datagen-related task list was byte-identical under both forms — `runDatagen` is the only
  datagen task in either case; the flag does not add, remove, or rename any task.
- The generated *output*, however, was not identical: under the flag-present form, `runDatagen`
  completed successfully and wrote the expected `en_us.json`. Under the bare form, `runDatagen`
  **failed outright** with `net.fabricmc.loader.api.LanguageAdapterException: ClassNotFoundException:
  transitreport.client.JollyalchemyTransitReportDataGenerator` and wrote zero files.

**Why:** this repo calls `loom { splitEnvironmentSourceSets() }`, and the datagen entrypoint class
lives in the **client** source set
(`src/client/java/transitreport/client/JollyalchemyTransitReportDataGenerator.java`). Without
`client = true`, the datagen run launches a classpath that does not include the client source
set, so it cannot even find the entrypoint class — it is not a partial degradation, it is a
complete failure to run any provider at all.

**Decision:** `client = true` is **kept** in `build.gradle`. On this project's specific
Loom 1.17 / Fabric API 0.92.12+1.20.1 / Minecraft 1.20.1 pairing, with a split client/common
source-set layout and a datagen entrypoint that lives in the client source set, the flag is load
-bearing — it is what makes the client source set visible to the datagen run at all, regardless of
whether Fabric's own current documentation lists it as a 1.21.4+ addition. This finding is scoped
to this project's configuration; a different provider layout (for example, one that puts the
datagen entrypoint entirely in the common source set) might not need it.
