# Development Guide

This file is the repo-local developer guide for the Human Design Transit Display mod. It exists
so that anyone returning to this repo after a break — including the author, who is new to
Minecraft mod development — can run the development loop, understand the JDK requirement, and
know what "verified" means for each phase without re-deriving any of it or re-litigating a
toolchain question that was already settled by observation. Update this file whenever the dev
loop, JDK requirement, or a toolchain finding changes.

## Running the dev client

Run:

```
./gradlew runClient
```

On PowerShell, use `.\gradlew.bat runClient` instead.

This is not a build check — it actually launches Minecraft. Loom compiles the mod, injects it
into a Fabric-loaded Minecraft 1.20.1 instance, and opens a real, playable game window. Its
working directory is this repo's `run/` folder, which is completely separate from the Minecraft
installed by the official launcher (a different `saves/`, `options.txt`, `mods/`, and `logs/`) —
nothing here touches your real `.minecraft` folder.

The `runClient` task does not exit until the game window is closed, so when it is driven by a
tool (rather than a human sitting at the keyboard) it should be started in the background and its
log tailed for readiness, rather than run in the foreground.

A reusable Creative Superflat dev world named `gsd-dev` already exists under `run/saves/gsd-dev`,
created during Phase 1 verification. Reuse this world for manual verification from Phase 2
onward instead of creating a new one each time.

## Running data generation

Run:

```
./gradlew runDatagen
```

Everything under `src/main/generated` is generated output. It is tracked in git (so reviewers and
CI can see what changed), but it is never hand-edited: to change its content, edit the provider in
`src/client/java/transitreport/client/JollyalchemyTransitReportDataGenerator.java` and re-run
`runDatagen` to regenerate the files.

The run currently produces exactly these files:

- `src/main/generated/assets/jollyalchemy-transit-report/blockstates/transit_chart.json` — the
  4-way `FACING` blockstate variants for `TransitChartBlock`, generated by the nested
  `TransitChartModelProvider`.
- `src/main/generated/assets/jollyalchemy-transit-report/models/block/transit_chart.json` — the
  block model, parenting `minecraft:block/orientable` with borrowed furnace textures, also
  generated by `TransitChartModelProvider`.
- `src/main/generated/assets/jollyalchemy-transit-report/models/item/transit_chart.json` — the
  block item's model, generated by the same `TransitChartModelProvider` — specifically by Fabric's
  own auto-item-model mechanism, not by any code written in that provider's `generateItemModels`
  override, which is intentionally left empty (see the finding below).
- `src/main/generated/assets/jollyalchemy-transit-report/lang/en_us.json` — the mod's English
  translation entries, generated by the nested `TransitReportLanguageProvider`. As of Phase 3 this
  carries not just the block name but the two tooltip lines as well (see below).
- `src/main/generated/data/jollyalchemy-transit-report/recipes/transit_chart.json` — the active
  shapeless single-dirt crafting recipe, generated by the nested `TransitChartRecipeProvider`
  (Phase 3, BLOCK-04/GEN-03).
- `src/main/generated/data/jollyalchemy-transit-report/advancements/recipes/misc/transit_chart.json`
  — the recipe-unlock advancement, emitted automatically alongside the recipe by the same
  `TransitChartRecipeProvider` call — not something the provider code asks for separately (Phase 3).
- `src/main/generated/data/jollyalchemy-transit-report/loot_tables/blocks/transit_chart.json` —
  the block's self-drop loot table, generated by the nested `TransitChartLootTableProvider`
  (Phase 3, BLOCK-05/GEN-04).
- `src/main/generated/.cache/` — Minecraft datagen's own internal cache/hash bookkeeping files,
  used to detect stale output between runs. Filenames are content-addressed, so they change
  whenever a provider's registered inputs change; file content also includes a regeneration
  timestamp, so it changes on every run even when the generated content itself does not — that is
  expected and not a sign of drift.

### Phase 2 data-generation findings

Settled by observation while building `TransitChartBlock` and `TransitChartModelProvider`
(RESEARCH.md Assumption A1 and Open Questions 1-2; full detail in
`.planning/phases/02-block-exists-and-places/02-01-SUMMARY.md`):

- **Assumption A1 — confirmed.** Leaving `generateItemModels` empty causes Fabric's model provider
  to auto-generate the block item's model as a plain parent reference to the block model
  (`{"parent": "jollyalchemy-transit-report:block/transit_chart"}`), with zero code required in
  that override.
- **Open Question 1 — confirmed.** `createHorizontallyRotatedBlock` paired with
  `TexturedModel.ORIENTABLE_ONLY_TOP` ran `runDatagen` clean end to end on the first attempt for
  this facing-only, no-`LIT` block — no deviation was needed.
- **Rejected: `createFurnace(Block, TexturedModel.Provider)`.** Hardcodes a
  `BlockStateProperties.LIT` boolean dispatch into the generated blockstate; `TransitChartBlock`
  has no `LIT` property (it extends `HorizontalDirectionalBlock`, not `AbstractFurnaceBlock`), so
  this helper does not match its state definition.
- **Rejected: `TexturedModel.ORIENTABLE`.** Requires a fourth `BOTTOM` texture slot this project
  has no texture for (only front/side/top furnace textures are borrowed); using it would leave the
  block's bottom face pointing at a nonexistent texture.

### Phase 3 data-generation findings

Settled by observation while building the recipe provider, the loot table provider, and the
tooltip override (03-RESEARCH.md Patterns 1-3; full detail in
`.planning/phases/03-craft-break-and-identify/03-01-SUMMARY.md` and `03-02-SUMMARY.md`). This
retires the MEDIUM-confidence `FabricRecipeProvider` method-shape risk that STATE.md and
ROADMAP.md have carried since roadmap creation — that risk is now closed.

- **`FabricRecipeProvider`'s 1.20.1 shape, confirmed.** The single abstract method to implement is
  `buildRecipes(Consumer<FinishedRecipe> exporter)` — not `generateRecipes`, and neither
  `ShapelessRecipeBuilder` nor `ShapedRecipeBuilder` takes a `CraftingBookCategory` argument on
  this Minecraft version. Both are post-1.21 shapes that simply do not exist here; current Fabric
  documentation and tutorials describe the newer signature.
- **`FabricBlockLootTableProvider`'s abstract method is the no-arg `generate()`.** A second,
  already-implemented `generate(BiConsumer<ResourceLocation, LootTable.Builder>)` method exists on
  the same class and must be left alone — it calls the no-arg `generate()` you write, then performs
  strict-validation bookkeeping that an accidental override of the `BiConsumer` overload would
  silently discard. Populate loot via `dropSelf(Block)` inside the no-arg override.
- **The recipe builder emits an advancement without being asked.** Calling
  `.save(exporter, id)` on the `ShapelessRecipeBuilder` produces both the recipe JSON and a
  recipe-unlock advancement JSON at `advancements/recipes/<category>/<id>.json` — the advancement
  is not a separate provider call.
- **The recipe JSON's `"category"` field is coarser than the source `RecipeCategory` enum
  constant** — several distinct enum constants can collapse to the same JSON category string. The
  advancement's file path (which folder the recipe category maps to) is the stronger, discriminating
  evidence of which category the builder actually used; check that path, not the recipe JSON's
  `category` field, when auditing which category a recipe was built with.
- **A block item's tooltip is attached by overriding the block, not by subclassing the item.**
  `BlockItem.appendHoverText` already delegates to `getBlock().appendHoverText(...)` — confirmed by
  disassembling the compiled `BlockItem` class. Overriding `Block.appendHoverText(ItemStack,
  BlockGetter, List<Component>, TooltipFlag)` directly on the existing block class is sufficient;
  no `BlockItem` subclass is needed and `TransitReportBlocks`'s construction of the block item is
  unchanged. Note the second parameter type is `BlockGetter` here — the item-level
  `appendHoverText` override (which most non-block-item tutorials show) takes `Level` instead, and
  writing that signature on a block compiles but is simply never called.

### Phase 4 rendering findings

Settled by observation while building `TransitChartBlockEntity` and `TransitChartRenderer`
(04-01-PLAN.md's "Corrections to 04-RESEARCH.md / 04-PATTERNS.md" section; full detail in
`.planning/phases/04-static-chart-rendering/04-01-SUMMARY.md`). This retires 04-01-PLAN.md's
Correction 9 open question (rotation sign) and records the API corrections most likely to recur
in Phase 6's dynamic texture pipeline.

**Rotation sign (Correction 9) — confirmed, no flip needed.** `Axis.YP.rotationDegrees(
-facing.toYRot())` — the negated form, Correction 9's default recommendation — is correct as
written. Confirmed against the real, asymmetric `sample-bodygraph.png` across all four horizontal
placements (north/south/east/west): the head-triangle points up and the image is never mirrored
left-right relative to the direction the block was placed facing, in every orientation. No sign
flip was needed at any point across this phase's several rounds of visual iteration (see design
deviations below) — the z/y-anchor changes made along the way are translations along local axes
that the rotation step itself never touches, so they had no bearing on the sign.

**D-06 (no size clamp) — confirmed no problem.** The single known 512x800 bundled image rendered
correctly at every orientation, distance, and lighting condition tested, with no stretching,
squashing, or other visible size-related defect. Deferring a sanity clamp to Phase 6/7 (once
arbitrary live-API image sizes are actually possible) cost nothing this phase.

**Four API corrections most likely to recur in Phase 6** (verified via `javap` against this
project's own compiled jars, per 04-01-PLAN.md's Corrections section — carried forward here so
Phase 6 does not have to re-derive them):

1. **`BlockEntity.getRenderBoundingBox()` does not exist on this Minecraft version.** It is a
   Forge-only API from older versions; grepping the full contents of both the client and common
   jars for `RenderBoundingBox` (any case) returns zero matches. The real mechanism for "this
   block entity's render extends past its own footprint and must not be culled" is
   `BlockEntityRenderer.shouldRenderOffScreen(T)` — a default interface method returning `false`,
   overridden to `true` on `TransitChartRenderer` (mirrors vanilla's `BeaconRenderer`).
2. **The emissive light constant is `net.minecraft.client.renderer.LightTexture.FULL_BRIGHT`**,
   not `LightmapTextureManager.MAX_LIGHT_COORDINATE` (the Yarn name; `LightmapTextureManager`
   does not exist in this jar at all).
3. **The Fabric renderer-registration class is
   `net.fabricmc.fabric.api.client.rendering.v1.BlockEntityRendererRegistry`**, not
   `BlockEntityRenderers`. One caveat worth carrying forward: `javap` confirms this entire class
   is itself marked `@Deprecated` in `fabric-rendering-v1 3.0.10+54550fb677` (the version this
   project resolves) — it still compiles and works correctly (confirmed by a clean `runClient`
   session with the renderer registered and rendering), so it was kept rather than chased into an
   undocumented replacement, but Phase 6 should expect this deprecation notice and not mistake it
   for a bug.
4. **A directly-bound (non-block-model) texture `ResourceLocation` must include the full
   `textures/...` prefix and the `.png` suffix** — e.g. `textures/block/transit_chart.png`, not
   `block/transit_chart`. This differs from the block-model `TextureSlot` convention (which strips
   both).

One more pattern worth carrying forward, found while resolving the design deviations below:
`BlockBehaviour`'s `getShape(...)` and `getRenderShape(...)` methods are themselves marked
`@Deprecated` on this Minecraft version (confirmed via `javap`) even though they are the correct,
intended override points — this is Mojang's own convention for marking "don't call this
directly, override it instead" methods, not a sign the API is going away. Vanilla's own
`WallBannerBlock` overrides `getShape(...)` the same way. Expect this deprecation notice
whenever overriding block shape/render-shape methods and do not treat it as a defect.

**Design deviations from the original plan, confirmed correct by direct user observation
in-game.** 04-01-PLAN.md's Task 1 action, as originally written, specified a full-cube block with
the chart floating in front of its `FACING` face, `BASE_WIDTH = 2.0f`, and a bottom-anchored quad
(D-05/D-08). After building that literally and reviewing it in a running client, the user
requested four rounds of iterative visual refinement, each verified in-game before the next was
attempted. The final, shipped design differs from 04-CONTEXT.md's locked decisions as follows:

- **Block is a thin, wall-hugging shape, not a full cube.** `TransitChartBlock.getShape(...)`
  returns a `VoxelShape` keyed by `FACING`, 2/16 of a block deep, hugging the face **opposite**
  `FACING` (the wall/mounting side) — not the default full 1x1x1 cube. Pattern and per-direction
  convention confirmed against vanilla's `WallBannerBlock` (`javap` against `Block.class`).
- **`getRenderShape(BlockState)` returns `RenderShape.INVISIBLE`.** The datagen'd cube model
  (Phase 2/3, still present and still generated) is suppressed entirely — only
  `TransitChartRenderer`'s floating quad is ever drawn for this block. This is deliberate and
  explicit, distinct from 02-CONTEXT.md's D-08 landmine (which is about `BaseEntityBlock`
  *silently* defaulting to `INVISIBLE` as a side effect of a base-class switch); this override is
  intentional and added directly on the `HorizontalDirectionalBlock` base already in use.
- **`TransitReportBlocks.TRANSIT_CHART`'s `Properties` now call `.noOcclusion()`.** Without it,
  vanilla's neighbor face-culling still treated the (now thin, invisible) block as occluding,
  leaving a rendering hole in the wall block behind it until an unrelated chunk rebuild (e.g.
  breaking the block) recalculated it.
- **Chart quad z-anchor is wall-flush (`Z_OFFSET` alone), not floating off the far face
  (`1.0f + Z_OFFSET`).** Once the block became invisible with its hitbox on the near/wall-side
  face, the quad had to move to that same face or it visibly floated a full block into the room.
- **Chart quad is vertically centered on the block's middle, not bottom-anchored.** Deviates from
  D-08's locked "bottom-anchored" decision. D-08's own reasoning assumed the original
  `BASE_WIDTH = 2.0f` (~3.1 blocks tall), where centering would have clipped into the floor; after
  the width was shrunk (next bullet), `computedHeight` (~2.34 blocks) no longer risks a floor-clip
  at this size, and centering reads correctly instead of "floating high" above the block.
- **`BASE_WIDTH` is `1.5f`, not `2.0f`.** Deviates from D-05's locked width value. Height still
  derives from this via the unchanged aspect-preserving formula, so it shrinks proportionally —
  no distortion was introduced.

All five deviations were requested and confirmed correct through direct in-game visual review
across four checkpoint rounds — they are refinements to a working implementation, not fixes to
broken behavior. REND-01 through REND-07 hold under the final, shipped design: the chart still
appears larger than the block's footprint, at its real aspect ratio, oriented per `FACING`
in all four horizontal directions, fully legible in total darkness, and visible without
popping/culling at the default 64-block render distance.

## JDK requirement

There are two separate JDK questions here, and conflating them is the most common setup mistake
for this generation of Fabric Loom:

- **What the mod compiles to:** Java 17 bytecode (`options.release = 17`, with
  `sourceCompatibility` and `targetCompatibility` both `VERSION_17` in `build.gradle`). This is
  fixed by Minecraft 1.20.1's own runtime requirement and must not change.
- **What runs the Gradle daemon that builds it:** independent of the line above, and only
  required to be JDK 17 or newer.

**JDK 26 is confirmed working end to end for this project.** Phase 1 verification (D-06) treated
"does JDK 26 actually run 1.20.1" as a real, pre-agreed risk — `./gradlew build` succeeding proves
nothing about it, since compiling to Java 17 bytecode never exercises LWJGL natives, Mixin's
bytecode manipulation, or 1.20.1 game code the way `runClient` does. The first `runClient` launch
on JDK 26 completed cleanly: no module access error, no LWJGL native load failure, no Mixin
reflection failure into JDK internals. The pre-agreed Temurin JDK 21 fallback was never triggered
and is not needed for this project.

If a JDK pin ever becomes necessary on a different machine, it belongs in that machine's local,
untracked `%USERPROFILE%/.gradle/gradle.properties` — never in this repository's tracked
`gradle.properties`. This repository has a public GitHub remote, and `.github/workflows/build.yml`
builds on `ubuntu-24.04` with JDK 25: a Windows absolute path in a tracked file would both fail
that build and publish the developer's local Windows username.

## What verified means for Phase 1

Verification passes only when **both** of the following hold, not just the first one:

1. The mod is listed on the in-game Mods screen (via Mod Menu, see the Phase 1 SUMMARY for why a
   dev-only Mods-screen dependency was added) under its display name, "Human Design Transit
   Display".
2. A world is created and actually entered — standing inside a loaded world, not just reaching
   the main menu.

Reaching the main menu is explicitly **not** sufficient. World load is where registries and
mixins are actually exercised; a mod that looks fine at the title screen can still fail the moment
a world loads. Treating "main menu opened" as done would hide exactly the failure mode this
verification step exists to catch.

## Datagen configuration finding

Phase 1 (TOOL-03) settled a disagreement between this project's own research documents:
`STACK.md` §1.4 called `fabricApi { configureDataGeneration { client = true } }` "current,
correct, already working" on the grounds that the build succeeds with it present; `PITFALLS.md`
Pitfall 2 observed that Fabric's own documentation describes `client = true` as a 1.21.4+
addition and expected it to no-op or fail on 1.20.1. Both observations were about
configuration-time acceptance, not runtime effect, so the question was settled by running both
forms and diffing what they actually produce, not by picking a document.

**What was compared:** the datagen-related task list from `./gradlew tasks --all` and the actual
generated output tree from a delete-and-regenerate `./gradlew runDatagen`, once with
`configureDataGeneration { client = true }` present and once with the bare
`configureDataGeneration()` form.

**What was observed:**

- The datagen-related task list was byte-identical under both forms — `runDatagen` is the only
  datagen task in either case; the flag does not add, remove, or rename any task.
- The generated *output*, however, was not identical: under the flag-present form, `runDatagen`
  completed successfully and wrote the expected `en_us.json`. Under the bare form, `runDatagen`
  **failed outright** with `net.fabricmc.loader.api.LanguageAdapterException: ClassNotFoundException:
  transitreport.client.JollyalchemyTransitReportDataGenerator` and wrote zero files.

**Why:** this repo calls `loom { splitEnvironmentSourceSets() }`, and the datagen entrypoint class
lives in the **client** source set
(`src/client/java/transitreport/client/JollyalchemyTransitReportDataGenerator.java`). Without
`client = true`, the datagen run launches a classpath that does not include the client source
set, so it cannot even find the entrypoint class — it is not a partial degradation, it is a
complete failure to run any provider at all.

**Decision:** `client = true` is **kept** in `build.gradle`. On this project's specific
Loom 1.17 / Fabric API 0.92.12+1.20.1 / Minecraft 1.20.1 pairing, with a split client/common
source-set layout and a datagen entrypoint that lives in the client source set, the flag is load
-bearing — it is what makes the client source set visible to the datagen run at all, regardless of
whether Fabric's own current documentation lists it as a 1.21.4+ addition. This finding is scoped
to this project's configuration; a different provider layout (for example, one that puts the
datagen entrypoint entirely in the common source set) might not need it.

## Installing the mod into real Minecraft (deferred)

client this guide otherwise covers) is deliberately deferred to the private-server distribution

installing Fabric Loader 1.20.1 via the official installer, adding Fabric API `0.92.12+1.20.1`,
