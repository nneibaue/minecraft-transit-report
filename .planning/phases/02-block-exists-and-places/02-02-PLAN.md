<objective>
## Phase Goal (MVP user story)

**As a** player on this server, **I want to** see the block I just placed named `Transit Chart` and pointing back at me from all four directions, **so that** I can tell at a glance that the block is really working before anything is drawn on its face.

> **Provenance:** the same planner-derived story as plan 02-01; the ROADMAP Phase 2 `**Goal:**` line is
> written as an outcome rather than in `As a / I want to / so that` form. Run `/gsd mvp-phase 02` if you
> want the canonical story written back into the ROADMAP.

This plan closes the phase. Plan 02-01 proved the block registers, places, and generates structurally
correct model JSON — but a structurally correct blockstate file is not the same claim as "the block draws
and orients correctly on screen", and this project's own convention (CLAUDE.md §7) is explicit that
rendered output has no practical automated assertion at this scale. Task 1 makes the block legible by
adding its display name, so that the visual check reads a real name rather than a raw key. Task 2 puts
the block in front of a human in a running dev client and records what the phase learned.

Purpose: D-07 pulls exactly one translation string forward from GEN-05's Phase 3 scope for precisely this
reason — the placement-and-facing verification is much harder to trust when the item is labelled with its
own translation key. D-05 then makes the four-direction check the phase's acceptance evidence, with the
Phase 1 protocol still in force: Claude launches the client in the background and tails the log, the user
watches the window and reports what they see.

Output: the block's display name in the generated language file, and a `docs/DEV.md` that tells the next
person what `runDatagen` produces and which data-generation questions this phase settled by observation.
</objective>
