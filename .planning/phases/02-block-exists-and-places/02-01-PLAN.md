<objective>
## Phase Goal (MVP user story)

**As a** player on this server, **I want to** take a Transit Chart block out of the creative inventory and place it against a wall so its face looks back at me, **so that** there is somewhere real for a chart to appear once the mod can draw one.

> **Provenance:** this story is planner-derived from the ROADMAP Phase 2 goal, not lifted from it. The
> ROADMAP `**Goal:**` line for this phase ("A display block exists in the game, can be taken from the
> creative inventory, and places itself facing the player") is written as an outcome, not in
> `As a / I want to / so that` form. Run `/gsd mvp-phase 02` if you want the canonical user story written
> back into the ROADMAP; nothing in this plan depends on that happening.

This plan is the phase tracer plus its correctness gate. Task 1 is the thin end-to-end slice: it wires
one path through every layer this phase touches — the block class and its facing state, the registry,
the creative tab, the data-generation provider, and the generated JSON that the running game actually
loads. Task 2 then proves that generated output is structurally right, tracked, and reproducible.

Purpose: nothing game-content-related exists in this repository yet. Phase 1 registered a mod
entrypoint and a language provider skeleton and stopped there. Every later phase in the display track
(3, 4, 6) hangs off a block that can be placed and that stores a facing value, so this is the slice
that has to be real before anything else can be built on it. RESEARCH.md settled two bytecode-verified
traps in the data-generation helpers that would each produce a plausible-looking failure — a malformed
property dispatch, or a single face rendering as the missing-texture checkerboard — and this plan
encodes both as concrete instructions rather than warnings.

Output: `TransitChartBlock`, a `TransitReportBlocks` registration holder wired into `onInitialize()`, a
`TransitChartModelProvider` wired into the datagen pack, and three generated JSON files under
`src/main/generated` that are proven correct and regenerable.
</objective>

  <action>
    Four files, then two Gradle runs. Write all four before running anything: the block, the holder, the
    entrypoint call, and the model provider are one slice, and `runDatagen` cannot generate a model for a
    block that is not yet constructed.

    **Create `src/main/java/transitreport/block/TransitChartBlock.java`**, package `transitreport.block`,
    `public class TransitChartBlock extends HorizontalDirectionalBlock`. Three members:
    - A public constructor taking `BlockBehaviour.Properties`, which calls `super(properties)` and then
      `this.registerDefaultState(this.stateDefinition.any().setValue(FACING, Direction.NORTH))`. Without
      that `registerDefaultState` call the block has no default facing and any placement path that does
      not go through `getStateForPlacement` — `/setblock`, a structure block — has no value to fall back on.
    - An override of `createBlockStateDefinition(StateDefinition.Builder&lt;Block, BlockState&gt; builder)`
      adding only `FACING`. `FACING` is inherited from `HorizontalDirectionalBlock` and is the same field
      object as `BlockStateProperties.HORIZONTAL_FACING`; reference the inherited `FACING`.
    - An override of `getStateForPlacement(BlockPlaceContext context)` returning
      `this.defaultBlockState().setValue(FACING, context.getHorizontalDirection().getOpposite())`. Per
      D-04 this is the furnace/chest convention — the front looks back at whoever placed it — and
      RESEARCH.md Pattern 2 confirms it is exactly what `AbstractFurnaceBlock.getStateForPlacement`
      compiles to. Do not substitute `getNearestLookingDirection()` or drop the `.getOpposite()`; both
      produce a block that is plausibly oriented and wrong, and Phase 4's renderer will be written
      against whatever this lands.

    Do not override `rotate` or `mirror` — `HorizontalDirectionalBlock` supplies both, and hand-rolling
    them risks subtly wrong math that only surfaces later under a structure block or a rotated
    `/setblock`. Keep the superclass as `HorizontalDirectionalBlock`: do not switch it to the block-entity
    base class `BaseEntityBlock`, which CONTEXT.md D-08 and RESEARCH.md Pitfall 4 record as a double
    regression — its `getRenderShape` default makes the block draw nothing at all, and it does not extend
    `HorizontalDirectionalBlock`, so the facing plumbing silently disappears at the same time. No
    `BlockEntity` and no `BlockEntityType` enter this phase; that is Phase 4's work (REND-01).

    **Create `src/main/java/transitreport/TransitReportBlocks.java`**, package `transitreport`,
    `public final class TransitReportBlocks` with a private no-arg constructor. Contents:
    - `public static final Block TRANSIT_CHART`, assigned `new TransitChartBlock(BlockBehaviour.Properties.of().strength(1.5F).sound(SoundType.AMETHYST))`.
      Per D-10 that is the complete property list: hardness in bookshelf/copper territory so the block is
      breakable but not instant, and the amethyst sound for a thematic tie to the intended recipe in
      REQUIREMENTS.md. Deliberately absent, and to stay absent: `requiresCorrectToolForDrops()` (Phase 3's
      loot table should drop it with any tool), `lightLevel(...)` (REND-05's legibility is a render-layer
      concern for Phase 4, not world illumination), and `noOcclusion()` (the model is a full opaque cube
      this phase and normal occlusion is correct).
    - `public static final Item TRANSIT_CHART_ITEM`, assigned `new BlockItem(TRANSIT_CHART, new Item.Properties())`.
    - `public static void register()`, which calls
      `Registry.register(BuiltInRegistries.BLOCK, JollyalchemyTransitReport.id("transit_chart"), TRANSIT_CHART)`,
      then the `BuiltInRegistries.ITEM` equivalent with the same id and `TRANSIT_CHART_ITEM`, then
      `ItemGroupEvents.modifyEntriesEvent(CreativeModeTabs.FUNCTIONAL_BLOCKS).register(entries -&gt; entries.accept(TRANSIT_CHART_ITEM))`.

    Build the `ResourceLocation` through `JollyalchemyTransitReport.id("transit_chart")`, not inline —
    that helper is the established convention and it is what keeps the namespace in one place. Per D-06
    the creative tab is vanilla's Functional Blocks tab, reached through Fabric API's item-group event; do
    not stand up a mod-owned `CreativeModeTab`. Creative-tab membership and survival availability are
    independent mechanisms in Minecraft — the tab is a testing convenience, and survival obtainability
    comes from the Phase 3 recipe (BLOCK-04) and loot table (BLOCK-05), both already scoped.

    **Edit `src/main/java/transitreport/JollyalchemyTransitReport.java`**: add a
    `TransitReportBlocks.register();` call inside `onInitialize()`, after the existing
    `LOGGER.info("Hello Fabric world!")` line. Keep that log line — Phase 01's launch verification greps
    for it and plan 02-02 greps for it again. No import is needed: `TransitReportBlocks` lives in the same
    `transitreport` package. This explicit call is load-bearing, not stylistic: Java does not run a class's
    static field initializers until the class is first touched, so a holder whose fields are only ever
    declared is a holder whose `Registry.register` calls never run. The failure mode is silent — the block
    is simply absent from the creative tab and unplaceable, with nothing logged (RESEARCH.md Pitfall 3).

    **Edit `src/client/java/transitreport/client/JollyalchemyTransitReportDataGenerator.java`**: add a
    second nested `private static final class TransitChartModelProvider extends FabricModelProvider`,
    mirroring the existing `TransitReportLanguageProvider` structure exactly (private static final nested
    class, private constructor taking `FabricDataOutput` and calling `super(output)`). It needs:
    - A private static final `TexturedModel.Provider` field, built from
      `TexturedModel.ORIENTABLE_ONLY_TOP.updateTexture(...)` with a lambda that calls `put` three times on
      the mapping: `TextureSlot.FRONT` to `new ResourceLocation("minecraft", "block/furnace_front")`,
      `TextureSlot.SIDE` to `block/furnace_side`, and `TextureSlot.TOP` to `block/furnace_top`. Those three
      vanilla textures are D-03's deliberate choice: no PNG is authored and no texture file is added to
      this repo this phase, and the furnace front's dark arched opening is what makes the four facing
      orientations visually distinguishable at all.
    - An override of `generateBlockStateModels(BlockModelGenerators blockModelGenerators)` calling
      `blockModelGenerators.createHorizontallyRotatedBlock(TransitReportBlocks.TRANSIT_CHART, &lt;that provider field&gt;)`.
    - An override of `generateItemModels(ItemModelGenerators itemModelGenerators)` left empty, with a
      comment stating that Fabric's model provider auto-generates the block item's model as a parent
      reference to the block model.

    Then add `pack.addProvider(TransitChartModelProvider::new);` in `onInitializeDataGenerator`, after the
    existing language-provider line. New imports required in this file:
    `net.fabricmc.fabric.api.datagen.v1.provider.FabricModelProvider`,
    `net.minecraft.data.models.BlockModelGenerators`, `net.minecraft.data.models.ItemModelGenerators`,
    `net.minecraft.data.models.model.TextureSlot`, `net.minecraft.data.models.model.TexturedModel`,
    `net.minecraft.resources.ResourceLocation`, and `transitreport.TransitReportBlocks`.

    **Two generator traps, both settled by bytecode disassembly in RESEARCH.md — read them before
    choosing a helper, because both alternatives look like the obvious match:**
    - Do not reach for `createFurnace(...)`. It is named after the furnace's specific two-state model and
      unconditionally builds a `BlockStateProperties.LIT` boolean dispatch into the generated blockstate.
      `TransitChartBlock`'s state definition has only `FACING`, so that dispatch has no property to bind
      to. `createHorizontallyRotatedBlock` is the pure facing-only helper and is the correct choice.
    - Do not reach for `TexturedModel.ORIENTABLE`. It is paired internally with the four-slot
      `ModelTemplates.CUBE_ORIENTABLE_TOP_BOTTOM` and its mapping fills a fourth `BOTTOM` slot that
      defaults to `jollyalchemy-transit-report:block/transit_chart_bottom` — a file D-03 guarantees does
      not exist. `TexturedModel.ORIENTABLE_ONLY_TOP` pairs with the three-slot `ModelTemplates.CUBE_ORIENTABLE`,
      which is the exact template vanilla's own shipped `furnace.json` uses.

    **Then run data generation and the build.** Run `./gradlew runDatagen`, then `./gradlew build`. If
    `runDatagen` throws inside model generation, that is the first trap's signature — fix the helper choice
    in the provider and re-run. Do not work around a generation failure by hand-authoring JSON under
    `src/main/resources`; that would fail ROADMAP Phase 2 criterion 4 silently while appearing to fix the
    problem. Finally `git add` the three new files under `src/main/generated` so the generated output is
    tracked, matching the convention Phase 01 established for `lang/en_us.json`.

## Flagged assumptions (edge-probe unresolved — surfaced, not dropped)

No `02-SPEC.md` exists for this phase, so the deterministic edge probe was run over the phase's
requirement IDs instead. It returned eleven rows. Nine were resolved into `must_haves.truths` above
(eight with explicit acceptance criteria, one as a `verification: backstop` marker covering creative-tab
ordering). Two came back **`unclassified` / `unresolved`**. An `unclassified` row is never auto-resolved
and never auto-dismissed, so both are surfaced here as explicit planner assumptions rather than silently
absorbed.

- **BLOCK-01 — edge dimensions not enumerated by any probe.** The probe's shape taxonomy (boundaries,
  adjacency, encoding, ordering) has no category for a requirement whose subject is placing a block in a
  voxel world. The planner assumption made here is that the only placement edges this phase owns are that
  placement succeeds against a normal solid face from any of the four horizontal approach directions, and
  that the resulting state carries a facing value. Everything else on the placement path — obstructed
  placement, replaceable blocks, waterlogging, placement against a non-solid face, placement in a
  protected region — is vanilla `BlockItem` and `BlockBehaviour` behaviour that this phase overrides
  nothing of and therefore does not test. That is planner judgement, not probe output, and it is not
  claimed to be exhaustive.

- **GEN-01 — edge dimensions not enumerated by any probe.** The planner assumption is that the generated
  blockstate/block-model pair is correct if and only if it has exactly four `facing=` variants with
  distinct quarter-turn y-rotations, no second property in any selector, and a three-slot texture map —
  which is to say, if and only if neither of the two bytecode-verified generator traps in RESEARCH.md
  fired. Other generation dimensions that exist in the format but not in this block's shape — multipart
  blockstates, tint indices, model overrides, custom element geometry, per-face UV rotation — are assumed
  out of scope because this block is a plain rotated cube. If Phase 4's oversized quad later needs a
  non-cube model, that assumption expires.

The probe's three generic category prompts (adjacency, empty, ordering) map poorly onto a block
registration phase and were translated into the domain question each actually implies here — tab-entry
uniqueness, default state in the absence of a placement context, and rotate/mirror determinism — rather
than answered literally. That translation is recorded in the corresponding `must_haves.truths` entries.
</flagged_assumptions>
