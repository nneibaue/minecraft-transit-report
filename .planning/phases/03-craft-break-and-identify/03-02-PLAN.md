<objective>
## Phase goal (MVP user story)

**As a** player on this server, **I want to** hover the Transit Chart in my inventory and read what it
is and what clicking it does, **so that** I know the block is interactive before I place it and start
waiting for something to happen.

> **Provenance:** this story is planner-derived from the ROADMAP Phase 3 goal, not lifted from it. The
> ROADMAP `**Goal:**` line for this phase is written as an outcome rather than in
> `As a / I want to / so that` form. Run `/gsd mvp-phase 03` if you want the canonical user story
> written back into the ROADMAP; nothing in this plan depends on that happening.

This plan is the second capability slice of the phase — the identify half. Task 1 wires the tooltip end
to end: two new translation keys generated into `en_us.json`, and a hover-text override on the block that
resolves them, with the italic style on the second line. Task 2 puts the whole phase in front of a person
in a running dev client — craft it from dirt, break it and get it back, hover it and read it — and writes
what was settled into `docs/DEV.md`.

Purpose: BLOCK-06 is the only requirement in this phase whose acceptance is a person reading words on a
screen. The mechanism behind it is small — one override, two translation entries — but two of its failure
modes are silent to every automated check available here. A key that exists in the Java source but not in
the generated language file renders the raw key, which looks like a bug to a player and like success to a
build. And an em-dash or curly apostrophe substituted into the translation value still resolves and still
renders; it just renders text nobody chose. Both are caught by asserting the generated file's exact bytes
and then by looking at it.

Output: `TransitChartBlock.appendHoverText`, two translation keys in the generated language file, and a
`docs/DEV.md` that records what data generation now produces across the whole phase.
</objective>

  <action>
    Two source files, then two Gradle runs.

    **Edit `src/main/java/transitreport/block/TransitChartBlock.java`**: append one override after the
    existing `getStateForPlacement` method — `public void appendHoverText(...)`, taking the item stack, a
    `BlockGetter`, a `List` of `Component`, and a `TooltipFlag`, in that order, returning void.

    Note the second parameter type carefully. The block-level method takes a `BlockGetter`, whereas the
    item-level method of the same name takes a `Level`. They are different methods on different classes.
    Writing the item-level signature here produces a method that compiles, carries no `@Override` error if
    the annotation is omitted, and is simply never called — the tooltip stays a bare name and nothing
    reports why. Include the `@Override` annotation so that mistake becomes a compile error instead of a
    silent no-op.

    The body adds exactly two entries to the tooltip list, in this order:
    1. A translatable component for the key `item.` + the mod id + `.transit_chart.tooltip`, with no
       styling — this is the functional line.
    2. A translatable component for the key `item.` + the mod id + `.transit_chart.flavor`, with the
       italic chat formatting applied — this is the flavour line.

    Build both keys by concatenating with `JollyalchemyTransitReport.MOD_ID` rather than writing the
    namespace as a literal, matching how every other key in this project is built. That import is new to
    this file. The other new imports the override needs are the chat formatting enum, the text component
    type, the item stack type, the tooltip flag type, the block-getter type, and `java.util.List`.

    Do **not** create a block-item subclass and do **not** touch `TransitReportBlocks`. Vanilla's block
    item already forwards its own hover text to the block it wraps — this was confirmed by disassembly, not
    inferred — so overriding the block's method is sufficient, and the registered item stays a plain block
    item constructed exactly as it is today. Most tooltip tutorials attach tooltips at the item class
    because that is where it goes for non-block items; following them here means changing registration for
    no gain.

    **Edit `src/client/java/transitreport/client/JollyalchemyTransitReportDataGenerator.java`**: add two
    entries to the existing `generateTranslations` body in `TransitReportLanguageProvider`, alongside the
    two already there. The keys are the same two the block override references — build them the same way,
    from the mod id constant. The values are exactly, character for character:

    - functional line: `Right-click to refresh.`
    - flavour line: `What the sky is doing, right now.`

    Type both with plain ASCII: an ordinary hyphen-minus in "Right-click", ordinary commas and periods, no
    typographic dash and no curly quotation marks. An autocorrected character still produces a file that
    parses, a key that resolves, and a tooltip that renders — it just renders something the author did not
    choose, and nothing downstream would flag it. The assertions below compare exact bytes for that reason.

    Leave the two existing entries untouched. The pre-existing refreshing string is a different string for
    a later phase's in-progress state; it is not a tooltip line, it is not to be reused as one, and it is
    not to be edited or removed here. There should be four entries in this method when you are done, not
    three and not two rewritten.

    **Then run data generation and the build.** Run `./gradlew runDatagen`, then `./gradlew build`. Confirm
    the regenerated `en_us.json` now holds four keys and that the two pre-existing values are unchanged.
    `git add` the regenerated file.

    If the build fails on the override, the most likely cause is the second parameter type — re-read the
    signature note above before changing anything else. If the build passes but the assertions on the
    generated file fail, the mismatch is between the key strings in the two files; fix whichever one drifted
    rather than adding a third key to bridge them.
