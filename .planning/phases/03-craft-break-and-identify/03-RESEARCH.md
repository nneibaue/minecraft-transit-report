## Summary

Phase 3 adds two new `FabricDataGenerator.Pack` providers to the existing `JollyalchemyTransitReportDataGenerator` entrypoint (`FabricRecipeProvider` for GEN-03/GEN-06, `FabricBlockLootTableProvider` for GEN-04), grows the existing `TransitReportLanguageProvider` with two new tooltip translation keys (GEN-05), and adds one small method override on the existing `TransitChartBlock` class (BLOCK-06). All three shapes were confirmed this session via `javap`/source-jar extraction against the exact jars this project compiles against — not against tutorials or current Fabric documentation, which describe post-1.21 signatures.

The single highest-value finding this session settles the MEDIUM-confidence risk flagged in ROADMAP.md/STATE.md: **`FabricRecipeProvider`'s 1.20.1 shape is `extends RecipeProvider` with a single abstract method `buildRecipes(Consumer<FinishedRecipe> exporter)`.** No `CraftingBookCategory` parameter exists on `ShapedRecipeBuilder`/`ShapelessRecipeBuilder` in this Minecraft version (that's a later-version concern) — the constructors and builders are exactly `RecipeCategory` + `ItemLike` + optional count, confirmed via `javap` against both the Fabric API jar (which ships full sources) and the Minecraft common jar.

The second finding: **`FabricBlockLootTableProvider.generate()` takes no arguments** (not `generate(BiConsumer<...>)` — that's a separate, already-implemented method the abstract subclass does not touch) and the correct one-line self-drop is `dropSelf(Block)`, inherited from vanilla's `BlockLootSubProvider`.

The third and most consequential finding, because it changes the planner's file-touch list from CONTEXT.md's Integration Points section: **no custom `BlockItem` subclass is needed for the tooltip.** `BlockItem.appendHoverText` was disassembled and confirmed to delegate to `getBlock().appendHoverText(...)` after calling `super.appendHoverText(...)`. `Block.appendHoverText(ItemStack, BlockGetter, List<Component>, TooltipFlag)` is a plain, non-final, overridable method with an empty default body. Overriding it directly on the already-existing `TransitChartBlock` class is simpler than subclassing `BlockItem` and requires zero change to `TransitReportBlocks.TRANSIT_CHART_ITEM`'s construction.

**Primary recommendation:** add `TransitChartRecipeProvider` (nested class, `extends FabricRecipeProvider`, single `ShapelessRecipeBuilder.shapeless(RecipeCategory.MISC, TRANSIT_CHART_ITEM).requires(Items.DIRT).unlockedBy(...).save(exporter, id)` call, thematic `ShapedRecipeBuilder` call commented out directly below it) and `TransitChartLootTableProvider` (nested class, `extends FabricBlockLootTableProvider`, `generate() { dropSelf(TRANSIT_CHART); }`) to `JollyalchemyTransitReportDataGenerator`, register both via `pack.addProvider(...)`; add two translation keys to the existing language provider; override `appendHoverText` directly on `TransitChartBlock`.

**When to use:** Any new crafting recipe this project adds.

### Anti-Patterns to Avoid

- **Subclassing `BlockItem` to add tooltip text:** unnecessary — `BlockItem.appendHoverText` already delegates to `Block.appendHoverText`. See Pattern 3.
- **Calling `FabricBlockLootTableProvider.generate(BiConsumer<...>)`:** that method already exists with a complete, correct implementation (it calls the no-arg `generate()` you implement, then does strict-validation bookkeeping). Overriding it instead of the no-arg `generate()` breaks that bookkeeping.
- **Leaving both the active and thematic recipes active simultaneously:** both target the same recipe id in the example above; `runDatagen` throws `IllegalStateException("Duplicate recipe ...")` if both are uncommented at once. See the inline comment in Pattern 1's example.
- **Reusing `text.jollyalchemy-transit-report.refreshing` for the tooltip:** that key is reserved for a later phase's in-progress/loading state per D-02's explicit note — use new, separate keys.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Recipe JSON | Hand-written `data/.../recipes/transit_chart.json` | `ShapelessRecipeBuilder`/`ShapedRecipeBuilder` inside a `FabricRecipeProvider` | Directly required by GEN-03/GEN-06 ("produced by data generation, not hand-written"); the builder API also validates recipe shape at datagen time rather than at runtime. |
| Loot table JSON | Hand-written `data/.../loot_tables/blocks/transit_chart.json` | `dropSelf(Block)` inside a `FabricBlockLootTableProvider` | Directly required by GEN-04; `dropSelf` is the exact vanilla one-liner for "drops itself, no tool restriction" and is what every no-special-drop vanilla block uses internally. |
| Tooltip text delivery mechanism | A custom `BlockItem` subclass, or hardcoded English strings passed to `Component.literal(...)` | `Block.appendHoverText` + `Component.translatable(...)` + generated language JSON | Directly required by GEN-05 (translation strings from data generation) and success criterion 3 ("no raw translation keys appear anywhere") — `Component.translatable` resolves through the generated `en_us.json`, `Component.literal` would not. |

**Key insight:** Every artifact this phase needs (recipe JSON, loot table JSON, tooltip translation keys) has a direct, purpose-built Fabric/vanilla datagen API — the work is picking the correct abstract method to override (`buildRecipes` vs. `generate()` vs. `generate(BiConsumer)`) and the correct class to attach behavior to (`Block` vs. `BlockItem`), not writing JSON or English strings directly.

## Common Pitfalls

### Pitfall 1: Overriding the wrong `generate` method on `FabricBlockLootTableProvider`

**What goes wrong:** `FabricBlockLootTableProvider` (via `BlockLootSubProvider`) has both an abstract no-arg `generate()` and an already-implemented `generate(BiConsumer<ResourceLocation, LootTable.Builder>)`. Overriding the latter by mistake (its signature is superficially similar and appears in the same class) discards the strict-validation and `BuiltInLootTables.EMPTY`-filtering logic Fabric already wrote for you, and if not implemented correctly, the loot table will never be populated at all.
**Why it happens:** Two `generate` methods with different arities on the same class, one abstract (implement this) and one concrete (do not touch), both named identically.
**How to avoid:** Override only `public void generate()` — no arguments. Populate loot via `dropSelf(block)` or other `BlockLootSubProvider` helpers, which write into the protected `map` field that the concrete `generate(BiConsumer)` already reads from.
**Warning signs:** `./gradlew runDatagen` succeeds but no `loot_tables/blocks/transit_chart.json` file appears, or (if strict validation is on) a build failure citing a missing loot table for `transit_chart` despite code appearing to add one.

### Pitfall 2: Both recipes active at once after uncommenting GEN-06's thematic recipe

**What goes wrong:** If a future edit uncomments the thematic `ShapedRecipeBuilder` block without also removing/commenting the active `ShapelessRecipeBuilder` block, both `.save(exporter, ...)` calls target the same recipe id (`transit_chart`). `FabricRecipeProvider.run()` tracks generated recipe ids in a `Set` and throws `IllegalStateException("Duplicate recipe " + identifier)` the moment the second one is submitted.
**Why it happens:** GEN-06 asks for "swapping is uncommenting rather than rewriting," which could be misread as "just uncomment, leave the rest as-is" rather than "uncomment to replace."
**How to avoid:** The inline comment directly above the thematic recipe block (see Pattern 1's code example) explicitly calls this out. When actually swapping, comment out or delete the active `ShapelessRecipeBuilder` call at the same time as uncommenting the thematic one.
**Warning signs:** `./gradlew runDatagen` throwing `IllegalStateException: Duplicate recipe jollyalchemy-transit-report:transit_chart` immediately after an edit to the recipe provider.

### Pitfall 3: Reaching for a custom `BlockItem` subclass for the tooltip

**What goes wrong:** Time spent designing and wiring a `TransitChartBlockItem extends BlockItem` with an `appendHoverText` override, then updating `TransitReportBlocks.TRANSIT_CHART_ITEM`'s construction and any code that references the concrete type — all unnecessary.
**Why it happens:** Most "add a custom tooltip" tutorials (and CONTEXT.md's own Integration Points note, written before this research settled the question) assume the item class is where tooltips are attached, since that's true for standalone (non-block) items.
**How to avoid:** For a `BlockItem`, override `Block.appendHoverText` on the block class instead — `BlockItem.appendHoverText` already forwards to it. See Pattern 3.
**Warning signs:** None at runtime (a `BlockItem` subclass approach would also work) — this is a design-time efficiency pitfall, not a correctness one. Flagged here purely to save implementation time and avoid an unnecessary registration change.
