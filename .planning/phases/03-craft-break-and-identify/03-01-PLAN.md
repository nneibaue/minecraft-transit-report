<objective>
## Phase goal (MVP user story)

**As a** player on this server, **I want to** craft a Transit Chart from a block of dirt and break it
back into my inventory, **so that** I can put one up, move it, and try it somewhere else without
switching to creative mode.

> **Provenance:** this story is planner-derived from the ROADMAP Phase 3 goal, not lifted from it. The
> ROADMAP `**Goal:**` line for this phase ("The block completes the survival loop — craftable,
> breakable back into itself, and named in the player's own language") is written as an outcome, not in
> `As a / I want to / so that` form. Run `/gsd mvp-phase 03` if you want the canonical user story
> written back into the ROADMAP; nothing in this plan depends on that happening.

This plan is the phase tracer plus its correctness gate. Task 1 is the thin end-to-end slice for the
survival half of the phase: dirt in a crafting grid produces the block, and breaking the block produces
the item, wired through every layer that path crosses — the datagen entrypoint, two new providers, the
generated JSON on disk, and a green build. Task 2 then proves that generated output is structurally
right, tracked, and reproducible.

**Why the tooltip is not in this tracer.** The identify half of the phase (BLOCK-06, GEN-05) is a second,
independent capability whose layer path does not overlap this one: it runs through a `Block` method
override in `src/main` and the language provider, and touches neither the recipe nor the loot table.
Folding it in would batch two unrelated end-to-end paths into one task, which is exactly what a tracer
slice avoids. It is plan 03-02, in wave 2 — sequenced after this one because both plans edit
`JollyalchemyTransitReportDataGenerator.java`.

Purpose: the block is currently creative-only. Every remaining phase in the display track is verified by
placing one and looking at it, and until this lands, doing that in survival means switching game mode.
The single-dirt recipe is a deliberate testing convenience so iteration never requires gathering
materials — REQUIREMENTS.md is explicit that it is expected to be replaced, which is why the real recipe
ships beside it as commented-out code rather than as a note in a document.

Output: two new nested providers in the datagen entrypoint, and three generated JSON files under
`src/main/generated/data` proven correct, tracked, and regenerable.
</objective>

**Mappings note (applies to every identifier in this plan):** this project compiles against Mojang
official mappings (`loom.officialMojangMappings()`), not Yarn. Every class and method name written below
is a Mojmap name and resolves against the jars under `.gradle/loom-cache/`. CLAUDE.md §2 carries the
translation table and the working practice: when documentation and resolved sources disagree, the
resolved sources win. This matters more than usual here — current Fabric documentation and essentially
every recipe-provider tutorial online describe a post-1.21 builder that takes a crafting-book category
argument and a `RecipeOutput` exporter. Neither exists in 1.20.1. 03-RESEARCH.md settled the 1.20.1

    **Add a nested `private static final class TransitChartRecipeProvider extends FabricRecipeProvider`**,
    placed after the existing `TransitChartModelProvider` class, with a private constructor taking
    `FabricDataOutput` and calling `super(output)` — the same shape the two existing providers use. It
    overrides exactly one method: `public void buildRecipes(Consumer&lt;FinishedRecipe&gt; exporter)`.

    That signature is the finding this phase inherited as an open risk and that 03-RESEARCH.md closed. On
    1.20.1 `FabricRecipeProvider` extends `RecipeProvider` and its single abstract method is
    `buildRecipes` taking a `Consumer` of `FinishedRecipe`. It is not named `generateRecipes`, and the
    parameter is not a `RecipeOutput` — that type does not exist in this version. Neither builder used
    below takes a crafting-book category argument either; the tutorials that show one are describing a
    later Minecraft.

    Inside `buildRecipes`, one active recipe:
    - `ShapelessRecipeBuilder.shapeless` with `RecipeCategory.MISC` and `TransitReportBlocks.TRANSIT_CHART_ITEM`
    - `.requires(Items.DIRT)` — one ingredient, which is what makes it a 2x2-grid recipe and satisfies
      BLOCK-04's "no crafting table required". A shapeless recipe with one ingredient fits any grid size
      the game offers; there is nothing extra to declare to make the inventory grid accept it.
    - `.unlockedBy("has_dirt", has(Items.DIRT))` — `has` is a static method inherited from `RecipeProvider`,
      so call it unqualified. This is not optional decoration: the builder validates on save and throws
      when a recipe is saved with no unlock criterion.
    - `.save(exporter, JollyalchemyTransitReport.id("transit_chart"))` — build the id through the existing
      helper, never as a literal namespaced string.

    Directly below the active recipe, **the thematic 3x3 recipe as commented-out code** (GEN-06). Use
    `ShapedRecipeBuilder.shaped` with `RecipeCategory.MISC` and the same result item, three `.pattern(...)`
    rows spelling `"AEA"` / `"ECE"` / `"AGA"`, four `.define(...)` calls binding `A` to
    `Items.AMETHYST_SHARD`, `E` to `Items.ECHO_SHARD`, `C` to `Items.CLOCK`, `G` to `Items.GLOW_INK_SAC`,
    an `.unlockedBy` on the echo shard, and a save call on the same id. That grid is copied from the
    Crafting Recipe section of REQUIREMENTS.md — four amethyst shards, three echo shards, one clock at the
    centre, one glow ink sac — and it is not to be adjusted. Every line of it is prefixed with `//` so the
    whole block is inert.

    Above that commented block, write a short comment explaining what it is and how to swap it in: the
    active call above must be commented out or removed **at the same time** as this one is uncommented,
    because both target the same recipe id and the provider throws on a duplicate id the moment the second
    one is submitted. Write that explicitly. "Swapping it in is uncommenting rather than rewriting" is
    genuinely misreadable as "just uncomment and leave everything else alone", and that reading produces a
    `runDatagen` failure whose message is clear but whose cause is not.

    **Add a nested `private static final class TransitChartLootTableProvider extends FabricBlockLootTableProvider`**,
    same nesting and same constructor shape, overriding `public void generate()` — **no arguments** — with
    a single statement: `dropSelf(TransitReportBlocks.TRANSIT_CHART)`.

    The arity is the trap here. This class carries two methods named `generate`: the no-argument one, which
    is abstract and is the one to implement, and a second one taking a `BiConsumer`, which Fabric has
    already written and which internally calls the no-argument one before doing its strict-validation
    bookkeeping. Overriding the `BiConsumer` variant compiles cleanly and discards that bookkeeping.
    `dropSelf` is inherited from vanilla's block-loot base class and is the exact one-line helper for
    "drops itself, no tool restriction" — do not hand-assemble the equivalent loot pool, and do not reach
    for the silk-touch variant, which introduces a drop branch nobody asked for.

    **Register both providers** by adding two `pack.addProvider(...)` lines in `onInitializeDataGenerator`
    after the two existing ones, one per new provider, in the same style. A provider that is written but
    never added to the pack produces no files at all while `runDatagen` still exits 0 — the failure is
    silent and looks exactly like a provider that ran and had nothing to generate.

    **New imports**, placed in the file's existing groups: `FabricRecipeProvider` and
    `FabricBlockLootTableProvider` alongside the other datagen provider imports;
    `net.minecraft.data.recipes.FinishedRecipe`, `net.minecraft.data.recipes.RecipeCategory`,
    `net.minecraft.data.recipes.ShapelessRecipeBuilder`, and `net.minecraft.world.item.Items` in the
    `net.minecraft.*` group; `java.util.function.Consumer` in its own group. `ShapedRecipeBuilder` is only
    referenced from inside a comment, so it needs no import while the thematic recipe stays commented out —
    add it at the moment the swap happens, not now.

    **Then run data generation and the build.** Run `./gradlew runDatagen`, then `./gradlew build`.

    Expect **three** new files, not two. The recipe builder emits a recipe-unlock advancement alongside the
    recipe itself, under `advancements/recipes/misc/`, where the folder segment comes from the recipe
    category's own folder name. After the run, enumerate what actually appeared — `git status --porcelain
    src/main/generated` is the direct way to see it — and `git add` every new file. Do not assume the file
    list is only the paths this action names; read it off the working tree and record what you found in the
    SUMMARY. If a fourth file appears that this plan does not predict, that is information worth writing
    down, not a problem to suppress.

    If `runDatagen` fails, read the exception before changing anything. A duplicate-recipe throw means both
    recipes are live. A missing-loot-table throw means the loot provider was written but not registered, or
    the wrong `generate` overload was overridden. Neither is fixed by writing JSON by hand under
    `src/main/resources` — that would satisfy the game and fail the requirement, and it would do so without
    any visible symptom.

  2x2-craftable — and that it produces exactly one output item. Everything else on the crafting path
