## Phase Goal (MVP user story)

**As a** developer on this mod, **I want to** run data generation and get real resource files written to
disk, **so that** every later phase can add blockstates, models, recipes, loot tables, and translations
as generated output instead of hand-written JSON.

> **Provenance:** this story is planner-derived from the ROADMAP Phase 1 goal, not lifted from it. The
> ROADMAP `**Goal:**` line for this phase is written as an outcome, not in `As a / I want to / so that`
> form. Run `/gsd mvp-phase 01` if you want the canonical user story written back into the ROADMAP.

Purpose: `runDatagen` currently exits 0 and writes nothing. `onInitializeDataGenerator()` has an empty
body, so zero providers are registered and `src/main/generated` does not exist at all. TOOL-02 says
generated resources must be *present* under `src/main/generated`, which means the requirement is
unsatisfiable as the repo stands — the task can pass its exit code and fail its actual criterion. This
plan registers the one provider that needs no block, item, or model to exist, so the requirement becomes
satisfiable without pulling any Phase 2 work forward (D-12).

Output: a `FabricLanguageProvider` registered in the datagen entrypoint, and a tracked
`src/main/generated/assets/jollyalchemy-transit-report/lang/en_us.json` that is provably regenerable
from it.
</objective>

  <action>
    **Step 1 — resolve the signature before writing any code** (D-12, and the project's standing
    "resolve against sources, not docs" convention). Locate the pinned data-generation module jar with
    `find ~/.gradle/caches -iname "*data-generation-api*.jar"`; for `fabric_api_version=0.92.12+1.20.1`
    the module is `fabric-data-generation-api-v1` at version `12.4.0+238242b777`, and the non-`-sources`
    jar is the one to read. Then run `javap -classpath <that jar> net.fabricmc.fabric.api.datagen.v1.provider.FabricLanguageProvider`,
    plus the same for `net.fabricmc.fabric.api.datagen.v1.FabricDataGenerator$Pack`,
    `net.fabricmc.fabric.api.datagen.v1.FabricDataGenerator$Pack$Factory`, and
    `net.fabricmc.fabric.api.datagen.v1.provider.FabricLanguageProvider$TranslationBuilder`.

    Planning already ran exactly those commands against this checkout, and the resolved shapes are below.
    Re-run them anyway and reconcile — if `javap` disagrees with any line here, `javap` wins and the
    disagreement goes in the SUMMARY:
    - `FabricLanguageProvider` is `public abstract`, implements the vanilla data-provider interface, and
      has two `protected` constructors: one taking a single `FabricDataOutput`, and one taking
      `FabricDataOutput` plus a `String` language code.
    - Its single abstract method is `public abstract void generateTranslations(FabricLanguageProvider.TranslationBuilder)`.
      It takes **one** parameter. There is no registry-lookup / `HolderLookup.Provider` parameter on this
      version — that parameter is a later-Fabric-API shape and code written for it will not compile here.
    - `FabricDataGenerator.createPack()` returns `FabricDataGenerator.Pack`.
    - `Pack.addProvider` is overloaded; the relevant overload takes a `Pack.Factory<T>`, whose single
      method is `T create(FabricDataOutput)`. A constructor reference to the one-argument
      `FabricDataOutput` constructor therefore satisfies it directly.
    - `TranslationBuilder.add(String, String)` is the key/value overload to use. The other overloads take
      Minecraft types (block, item, item-group key, entity type, …) that do not exist yet in this project.

    **Step 2 — write the registration.** In `onInitializeDataGenerator(FabricDataGenerator fabricDataGenerator)`,
    obtain a pack via `fabricDataGenerator.createPack()` and register the provider with
    `pack.addProvider(TransitReportLanguageProvider::new)`.

    Define `TransitReportLanguageProvider` as a `private static final` nested class inside
    `JollyalchemyTransitReportDataGenerator`, extending `FabricLanguageProvider`. Give it a constructor
    taking `FabricDataOutput` that delegates to `super(dataOutput)` — the one-argument form, which
    defaults to `en_us`. Override `generateTranslations(FabricLanguageProvider.TranslationBuilder)` and add
    exactly one entry: key `"text." + JollyalchemyTransitReport.MOD_ID + ".refreshing"`, value
    `Refreshing transit chart...`. Build the key from the existing `MOD_ID` constant rather than repeating
    the mod id as a string literal; CONTEXT lists `MOD_ID` as an already-correct reusable asset.

    A nested class, not a separate file: this project's constraints call for avoiding premature
    abstraction, and one provider does not need its own compilation unit. Phase 3's GEN-05 work grows this
    same class rather than replacing it, so the entry above is a skeleton, not scaffolding to throw away —
    `text.<modid>.refreshing` is the actionbar string REF-06 needs in Phase 10, and it needs no block,
    item, or model to exist, which is exactly why a language provider was chosen over any other provider
    type (D-12).

    New imports required beyond the two already present: `net.fabricmc.fabric.api.datagen.v1.FabricDataOutput`,
    `net.fabricmc.fabric.api.datagen.v1.provider.FabricLanguageProvider`, and
    `transitreport.JollyalchemyTransitReport`.

    **Step 3 — compile.** `./gradlew build` is the real signature check: if the constructor arity or the
    `generateTranslations` parameter list is wrong, compilation fails. Do not proceed to Task 2 on a
    failed build.

    Note for anyone new to Fabric: data generation is a build-time step. It runs the mod's datagen
    entrypoint in a headless harness and writes static JSON to disk, which then ships inside the jar. It
    has no connection to the runtime texture or HTTP work in later phases, and it structurally cannot
    represent bytes that only exist after a runtime network call.
  </action>
