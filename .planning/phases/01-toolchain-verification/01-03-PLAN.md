<objective>
## Phase Goal (MVP user story)

**As a** developer returning to this repo after a break, **I want to** open one file and learn how to run
the client, run data generation, and which JDK to use, **so that** I never have to re-derive the
development loop or re-litigate a toolchain question that was already answered once.

> **Provenance:** this story is planner-derived from the ROADMAP Phase 1 goal, not lifted from it. The
> ROADMAP `**Goal:**` line for this phase is written as an outcome, not in `As a / I want to / so that`
> form. Run `/gsd mvp-phase 01` if you want the canonical user story written back into the ROADMAP.

Purpose: two of this project's own research documents disagree about `configureDataGeneration { client = true }`.
STACK.md section 1.4 calls it "current, correct, already working" on the grounds that the build succeeds
with it present. PITFALLS.md Pitfall 2 observes that Fabric documents the flag as a 1.21.4+ addition. Both
can be true at once — configuration-time acceptance is not the same as runtime effect — so the question
cannot be settled by picking a document (D-13). It is settled by running both forms and diffing what they
produce. Whatever the answer, it then has to be written down, because the next person to read
`build.gradle` will otherwise re-open exactly this question.

Output: a `build.gradle` carrying the form that was proven to work, and `docs/DEV.md` — a repo-local
developer guide that outlives this phase and is where the deferred "install into real Minecraft"
walkthrough lands when the private-server milestone arrives.
</objective>

| Experiment scratch state → repository working tree | The comparison runs delete and regenerate `src/main/generated` and capture copies of it |
