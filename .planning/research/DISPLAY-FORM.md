# Display Form Factor: Oversized Quad vs. Projector

**Question:** Should the display render on the block's own face (oversized quad, painting-precedent), or float in the air away from the block (projector, "triggers the reading" as the owner put it)?

**Researched:** 2026-09-07
**Recommendation:** Oversized quad for v1. Projector is a real, buildable v1.x/v2 enhancement, not a v1 form factor. **This decision can be deferred at zero cost** — see §5.

---

## 1. Prior Art — who actually renders detached from the block, and what do they anchor to?

| Mod / mechanic | Does it float free of the block? | What it actually anchors to | Confidence |
|---|---|---|---|
| **Create: Display Board + Display Link** | **No — false friend.** "Link" here means a data link (which redstone-adjacent source block's value to read), not a spatial image link. Rendered text always stays glued to the Display Board's own face. | The Display Board block itself. Range (64 blocks, configurable) governs how far away the *source* of the data can be, not how far the *image* projects. | HIGH (verified via Create Wiki + live GitHub issue thread) |
| **WATERFrAMES "Projector"** (SrRapero720) | Likely partially — it's one of four display types (Frame, Projector, TV, Big TV) with its own rotate/transparency/brightness/audio-distance settings, and a filed bug ("disappearing projector screen") implies the projected screen is a distinct renderable surface from the emitting block. This is the closest real branding match to what the owner described. | Unclear from available material whether placement is a fixed configured offset, a manually-rotated screen, or a raycast-to-wall throw. **Could not verify the exact targeting mechanism** — treat this as suggestive, not confirmed, prior art. | LOW-MEDIUM (name and existence verified; mechanism not) |
| **Vanilla Beacon beam** | Extends far beyond the block's own 1×1×1 footprint (up to the world's build height), but straight up from the block's own position — not offset sideways into open air. | The beacon block's own position; only the *extent* of the rendered geometry is detached, not the anchor point. | HIGH for the existence/shape of the effect (vanilla, well-documented); MEDIUM for the exact override mechanism cited below (community-sourced, not decompiled in this session) |
| **End Gateway beam** | Same pattern as beacon — a vertical light-beam rendered far past the block's footprint. | Same as beacon: anchor point unchanged, only extent grows. | MEDIUM (same-pattern inference from beacon; not independently verified this session) |
| **Applied Energistics 2 terminals** | **No — not real prior art for this question.** ME/crafting terminals are 2D inventory GUI screens opened on right-click, not in-world floating holograms. There is no AE2 mechanic that projects a texture into open 3D space. | N/A | HIGH (ruled out, not a mechanism match) |
| **Origins / Extra Origins "hologram" effects** | **Could not verify.** Origins is a datapack-driven player-ability mod (elytra flight, echolocation, etc.); no block-anchored floating-image mechanic under this name was found. | N/A | LOW — treat as unverified, likely not applicable; not used as evidence either way |
| **Valkyrien Skies** | Yes, but at a completely different scale: entire multi-block ship assemblies render at a physics-driven transform decoupled from their nominal world-grid position, via a custom rendering pipeline that replaces vanilla's chunk-based render assumptions entirely. | A simulated rigid body, not a block. | HIGH (real, verified mod) — cited only as an **upper-bound cautionary comparison**: this is the scale of engineering true detached, physics-correct rendering actually takes. A single floating billboard quad needs none of it. |
| **Hologram plugins (HolographicDisplays, DecentHolograms) — Bukkit/Paper, not Fabric** | Yes, genuinely floats free of any block. | An **invisible marker entity** (armor stand) with a custom name tag, rendered by vanilla's own entity nametag billboard renderer. | HIGH (well-established plugin category) — cited as an **alternative architecture** the projector could use instead of a hand-rolled block-entity render override: spawning a client-side marker entity gets frustum culling correctness for free from the normal entity-rendering pipeline. **Rejected for this project** because it reintroduces entity spawn/track/despawn concerns that conflict with the "single logical block, not multi-entity" constraint in PROJECT.md — noted for completeness, not recommended. |

**Bottom line on prior art:** nothing in the surveyed ecosystem is a clean, verified example of "flat image floats in open air at a distance from its anchor block, no GUI, no entity." The closest real analog for the *technical* problem (render geometry far outside the block's own footprint without breaking culling) is vanilla's own beacon/gateway beams — genuine, verifiable, and directly reusable technique. The closest real analog for the *product concept* ("a projector block") is WATERFrAMES, but its exact targeting mechanism could not be confirmed from available sources.

## 2. Rendering mechanics — what actually changes

Fabric 1.20.1's block-entity-renderer method signature (verified against the Fabric wiki tutorial for this era, before the docs moved to the post-1.21 pipeline): `render(T blockEntity, float tickDelta, MatrixStack matrices, VertexConsumerProvider vertexConsumers, int light, int overlay)`. Mojang-mappings equivalent: `render(T blockEntity, float partialTick, PoseStack poseStack, MultiBufferSource bufferSource, int packedLight, int packedOverlay)`.

**Render bounding box.** `BlockEntity.getRenderBoundingBox()` (same name in Yarn and — per this project's own established genSources tie-break practice — expected identical in Mojang mappings, MEDIUM confidence pending verification against the resolved 1.20.1 jar) returns the `Box`/`AABB` Minecraft frustum-tests to decide whether to even call `render()` this frame. Default implementation is sized to the block's own position. **This is not a new problem the projector introduces — it's the same override the oversized quad already requires** (per this project's existing FEATURES.md dependency notes), just with a bigger and, if raycast-based, *variable* box instead of a small, static one decided once.
- Ceiling: there isn't a hard engine limit, but a box that's needlessly huge (e.g., "infinite" style overrides some vanilla block entities use) forces Minecraft to consider the block entity for rendering on every frame regardless of camera direction, which is fine for one block but is the kind of thing you don't want as a default habit. Practical ceiling for this project: a box tightly enclosing "the block position through the farthest point the image can ever appear," recomputed only when that farthest point changes (placement, or raycast retarget) — not recomputed per frame from scratch. For a fixed-offset design (a few blocks), this is trivial. For raycast-to-wall with no distance cap, size it to the render-distance limit as a backstop rather than truly unbounded.

**Does it still render when the anchor block is off-screen but the image is on-screen?** **Yes, concretely, provided the bounding box override above is done correctly** — this is exactly the mechanism vanilla's beacon beam relies on (multiple independent modding-community sources describe beacon-family block entities overriding `getRenderBoundingBox()` to a box far larger than their own footprint specifically so the beam doesn't vanish when the beacon block itself scrolls out of frame but the beam is still in view). The central risk isn't "is this possible" — it demonstrably is, in vanilla, today — the risk is that it's easy to get subtly wrong for a *moving/variable* target (raycast projection) versus vanilla's *fixed* beam extent, since the box must be recomputed whenever the projection target changes rather than set once at construction.

**`getRenderDistance()`.** A `default` method on the renderer interface, default 64 blocks — verified present across Yarn API docs from 1.17 through 1.21.5, i.e., stable across this whole span including 1.20.1. This check is a simple distance test **from the camera to the block entity's own position**, separate from the frustum/bounding-box check above. This produces a real, concrete quirk for the projector that the oversized quad never has: because the distance check is anchored to the block, not to the projected image,
- a long-throw raycast projection could have its *block* within 64 blocks while the *image* itself sits well beyond what would normally be rendered at that distance for content of that visual size (undercounts true distance to the visible content), and
- conversely, a projector far from the player (block >64 blocks away) but throwing its image toward the player would incorrectly stop rendering even though the image itself might be close and clearly should be visible.
Neither case is a crash or a real bug players would necessarily notice at "a few friends on a small private server" scale with short throw distances, but it's an honest asterisk specific to the projector form that doesn't exist for the oversized quad, where anchor and content position are always within about a block of each other.

**Depth, culling, occlusion, `RenderLayer`.** A floating quad in open air, unlike a quad glued to a block face, genuinely needs normal depth testing **enabled** so intervening terrain correctly occludes it — this matters far more here than for the face-mounted form, where the quad basically coincides with solid geometry anyway. The FEATURES.md anti-feature table already flags "visibility through walls" as something no reviewed mod does and this project must not do either; that constraint gets meaningfully harder to accidentally violate with a floating quad than a face-mounted one, because a depth-test-disabled/"see-through" render layer is a common shortcut for glow effects and it's the wrong one here. The right family of choice (Yarn) is `RenderLayer.getEntityTranslucentEmissive(textureId)` — an unlit/emissive but still depth-tested layer, the same category vanilla uses for glow-eye effects that still get correctly hidden behind walls (Mojmap equivalent expected to be `RenderType.entityTranslucentEmissive(ResourceLocation)`, MEDIUM confidence, standard modding pattern, verify name via genSources). Do **not** reach for a no-depth/"see-through" variant (the kind used for things like the ender dragon death beam) — that would directly recreate the anti-feature this project has already ruled out. Z-fighting is only a risk if a raycast-to-wall design lands the quad's plane exactly on a block's surface; the standard fix is a small epsilon offset off the hit surface, identical to how any decal-style renderer avoids this.

**Billboarding vs. fixed orientation.** Billboarding (rotating the quad each frame to face the camera, the nametag/particle-sprite idiom, done by applying the camera's rotation to the `MatrixStack` before drawing) is the *wrong* choice here, and it's also the more complex one — a rare case where "simpler" and "reads better" agree. A billboarded chart looks and behaves like a HUD element floating in the world (a nametag, a health bar) rather than a physical object with a front and back, which undercuts exactly the "projector as a real thing in the world" framing the owner is going for — and it means the image would face the player identically from above, behind, or the side, which is not how a projected beam works. Fixed orientation — set once from the block's placement facing, exactly like the oversized quad's existing orientation logic, just relocated in space — is both simpler (no per-frame camera-rotation math) and the better reading experience for content meant to be stood in front of and read, like a sign or painting.

## 3. Projection behavior — open design questions, framed not assumed

These are real forks the owner has not resolved yet; each has a genuine tradeoff.

- **Fixed offset vs. raycast-to-wall.** A fixed offset (translate the quad a constant vector from the block, e.g. "2 blocks in front of the facing direction") is a small, one-time addition on top of the oversized-quad baseline — a single `matrices.translate()` call with a static vector. Raycast-to-wall (the "real projector hitting a wall" framing) requires an actual world raycast (Yarn `World.raycast(RaycastContext)` / Mojmap `Level.clip(ClipContext)`), a no-hit fallback (what happens projecting into open sky — a max throw distance is the standard answer), and a decision about *when* to re-raycast: once at placement (cheap, but the image can end up floating through a wall someone builds later) or every tick/on world change nearby (correct-looking, but new logic with no equivalent in the fixed-offset or oversized-quad forms at all).
- **Always-on vs. toggled (redstone or right-click).** Always-on matches the oversized quad's behavior and PROJECT.md's Core Value ("keeps updating on its own") with zero new component surface. A toggle — whether redstone-driven (a new `BlockState` boolean property, `neighborUpdate`/redstone-power overrides) or right-click-driven (reuses the existing interaction handler, adds one flag) — raises a real, unresolved question either way: does the background fetch/refresh scheduler keep running while the display is hidden/off (so it's instantly current when re-enabled), or does it pause (saving pointless requests while intentionally off)? This needs an answer before a toggle is built; it doesn't need one for always-on.
- **Distance-based scaling.** Real projectors get bigger on a farther wall; this project's chart should not. A fixed world-space size regardless of throw distance matches the existing "fixed-aspect-ratio, never stretched" table-stakes requirement already established for the oversized quad, and is simpler — distance-based scaling is a wholly new computation (world-size as a function of throw distance and an assumed cone angle) that buys nothing for a chart meant to be consistently legible, whichever offset/raycast model is chosen.
- **Walking through the projection.** As a flat, non-solid quad with no collision (matching the vanilla end-gateway-beam precedent, which also has no collision), a player simply clips through it — no new collision logic needed. Normal depth testing (already required above) makes the player's own model correctly occlude the part of the image behind them as they walk through it, for free.

## 4. Complexity delta — quantified, not hand-waved

Both forms share an identical baseline that must exist regardless of which is chosen: facing block state, quad geometry + UV/aspect fit, texture binding, and an emissive render layer. That shared baseline is already scoped in FEATURES.md as MEDIUM complexity for the bounding-box override and MEDIUM for emissive rendering, LOW for the rest.

On top of that shared baseline, the **projector adds, concretely:**

| Addition | New vs. shared with oversized quad? | Relative cost |
|---|---|---|
| Translate quad to an offset point (fixed-offset variant) | New, but trivial — one extra `matrices.translate()` call | Near-zero |
| Bounding-box override sized to enclose a point *away* from the block, not just a small fixed enlargement | New complexity class — must handle an asymmetric, direction-dependent box instead of a small symmetric one | LOW-MEDIUM |
| World raycast + no-hit fallback + re-raycast policy (raycast-to-wall variant only) | Entirely new subsystem, no equivalent in the oversized-quad form at all | MEDIUM |
| Redstone/toggle `BlockState` + gating of renderer and refresh scheduler (toggle variant only) | Entirely new subsystem, no equivalent at all | LOW-MEDIUM |
| A visible "throw" cue (beam, cone, glow) from block to image | **Effectively required for the concept to read as intended** — a chart floating in space with no visible source looks like a bug, not a projector. This is a second render primitive, wholly new. | MEDIUM-HIGH, and is squarely the kind of decorative/visual-polish work PROJECT.md explicitly defers |

Net assessment: the projector is not a small increment on the oversized quad — it is the oversized quad's **entire scope, plus two to four largely independent new subsystems**, at least one of which (the throw cue) is required for the form to actually deliver the product idea the owner is picturing, and that one falls squarely inside the "decorative modeling and visual polish... deferred until the dynamic texture pipeline works end-to-end" line already drawn in PROJECT.md.

**Which reaches a working, satisfying result first:** the oversized quad, unambiguously. It reuses 100% of the rendering work that must be built regardless (facing, bounding box, emissive layer) with the smallest possible increment on top. The projector, built to a standard that actually reads as "a projector" rather than "a chart bug," requires meaningfully more net-new work, some of which is explicitly out of scope for this milestone by PROJECT.md's own stated priorities.

**Verdict on staging:** the projector is a v1.x/v2 enhancement layered onto a working pipeline, not a v1 form factor.

## 5. Compatibility — does this decision touch anything else?

**No.** The HTTP client, texture manager, and refresh scheduler operate identically regardless of where the resulting texture gets drawn: PNG bytes → `NativeImage`/`NativeImageBackedTexture` → bound texture is unaffected by whether the renderer later translates the quad zero blocks or five blocks from the block face. Config (base URL, refresh interval) is likewise untouched. PROJECT.md's own separation-of-concerns constraint — "the renderer never performs HTTP; the HTTP client never manipulates rendering state" — already draws exactly the boundary that makes this true: display form is entirely contained inside `TransitDisplayRenderer` (and, only if a toggle or raycast-target is added later, a small amount of new state on `TransitDisplayBlockEntity`/`TransitDisplayBlock`). Nothing about `TransitApiClient`, `TransitTextureManager`, or `TransitRefreshScheduler` changes.

**This means the decision can be safely deferred at zero cost.** Build the dynamic texture pipeline against the oversized-quad renderer — the smallest correct implementation, reusing vanilla's own painting/beacon-family precedents directly — and treat the projector as a later, additive rendering variant (a second `BlockEntityRenderer` implementation, or a swapped code path within the existing one) once the pipeline is proven end to end. Nothing decided now forecloses it.

---

## Recommendation

**Build the oversized quad for v1.** It is the smaller, better-precedented, fully-scoped path to a working display, and it does not compromise the projector's future viability in any way.

**Defer the projector decision — do not make it now.** It touches only the renderer's transform and bounding box; every other component (HTTP client, texture manager, scheduler, config) is identical either way. Revisit it after the texture pipeline works end to end, and only build it with a visible throw/beam cue — without one, a floating chart with no visible source reads as broken, not as a projector.
