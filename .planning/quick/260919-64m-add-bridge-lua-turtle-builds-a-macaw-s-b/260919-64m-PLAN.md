<action>
Write `turtle/bridge.lua` implementing the full specification below. Use section-banner
comments like `tunnel.lua`/`crater.lua` (Config / State / Heading & movement / Inventory &
fuel / Biome markers / Column building / Resume & probe / Going home / Main). Target roughly
350-500 lines with real comments, not padding.

=== HEADER COMMENT ===
Title banner ("Macaw's balustrade bridge builder") plus a short description: builds a
floating bridge outward from a start block, labels biome changes with a marker + sign,
returns home when out of pieces. Then:
- Setup: turtle upgrades — one side an Advanced Peripherals Environment Detector, the other
  a pickaxe (clears obstacles ahead and is used by the resume probe). Inventory (any slots,
  matched by name, re-scanned as needed): bridge pieces (name contains "bridge" — e.g.
  Macaw's Bridges balustrade cobblestone bridge), signs (name contains "sign"), fuel (any
  item `turtle.refuel(0)` accepts), and optionally marker blocks (see Inventory section
  below). Start: place the turtle ON TOP of `blue_skies:vitreous_moonstone`, facing the
  direction to build.
- Usage: `bridge` (start/resume building), `bridge reset` (forget saved progress — deletes
  the state file and stops; run `bridge` again to start fresh), `bridge status` (print the
  saved state and exit without moving).

=== CONFIG BLOCK ===
- `BRIDGE_MATCH = "bridge"` — bridge pieces are any item whose name contains this.
- `MARKER_MATCH = nil` — biome marker block; `nil` means auto-pick (see Inventory).
- `MARKER_SIDE = "right"` — `"left"` or `"right"`, which side of the bridge gets markers.
- `WIDTH = 1` — extra lanes are built to the RIGHT of lane 0.
- `REPLACE_TERRAIN = false` — if true, dig existing terrain under the deck before placing.
- `MAX_LENGTH = 0` — 0 = unlimited blocks before turning back.
- `FUEL_LOW = 200`, `FUEL_TARGET = 2000`, `FUEL_MARGIN = 50`.
- `STATE_FILE = "bridge_state.txt"`.

=== STATE ===
Fields, serialized with `textutils.serialize`/`unserialize` via `fs.open`/`readAll` (mirror
`tunnel.lua`'s `saveState`/`loadState`): `dist` (blocks from home along the bridge), `lane`
(current sidestep offset, 0 = the main line), `heading` (one of `"out"|"back"|"left"|"right"`
— relative to the direction the turtle first faced, NOT a compass direction — see Heading
below), `built` (the furthest column known finished, used to fast-travel on resume),
`lastBiome` (string or nil), `homeBlock` (the block name seen under the turtle at first run),
`fOut` (the world compass facing — `"north"|"east"|"south"|"west"` — of "out", captured from
the first bridge piece's own `state.facing` right after it is placed; nil until then), and
per-run counters `placed`, `signs`. Call `saveState()` both immediately before and
immediately after every turtle move or turn that changes `dist`/`lane`/`heading` (the
`crater.lua` pattern), so a mid-move reboot never leaves the file inconsistent with where the
turtle actually is.

=== HEADING MODEL (no compass sense) ===
A turtle cannot read its own facing, so `heading` tracks facing RELATIVE to the direction the
turtle faced when it started (its `"out"`), using the fixed ring `out -> right -> back -> left
-> out`. Implement two primitives that both call `saveState()` before and after:
- `turnR()`: `turtle.turnRight()`, then advance `heading` one step forward through the ring.
- `turnL()`: `turtle.turnLeft()`, then advance `heading` one step backward through the ring.
- `faceRel(target)`: turns the short way (0, 1, or 2 calls to `turnR`/`turnL`) until
  `heading == target`.
This ring is also how the resume probe (below) recovers `heading` after a reboot, and how the
biome-marker detour below is proven to return to the exact starting cell/orientation without
needing its own bookkeeping.

=== MOVEMENT / OBSTACLES ===
`forward()`: obstacle-clear at turtle level only (tunnel.lua's `clear`/`push`: dig-loop with
a bedrock/stubborn give-up after ~10-20 tries, `turtle.attack()` for mobs blocking the way,
`sleep(0.1-0.2)` between attempts). NEVER call `digDown`/`digUp` as part of this generic
clearing, and never dig a block whose name contains `BRIDGE_MATCH` or `"sign"`, equals the
recorded `homeBlock`, or matches the resolved marker item name — if the obstacle ahead is one
of those, treat it like bedrock (give up, report clearly) rather than destroy it. On a
successful step, update position before saving: `heading == "out"` -> `dist += 1`;
`"back"` -> `dist -= 1`; `"right"` -> `lane += 1`; `"left"` -> `lane -= 1`. `forward()` is
used for all bridge-line and lane-sidestep travel; the biome-marker detour (below) does NOT
use it — it makes its own raw, symmetric moves.

=== INVENTORY HELPERS ===
`findSlot(kind)` scans slots 1-16 with `turtle.getItemDetail(slot)`, re-scanning every time a
kind is needed (no cached slot numbers): `"bridge"` -> name contains `BRIDGE_MATCH`; `"sign"`
-> name contains `"sign"`; `"fuel"` -> `turtle.select(slot)` then `turtle.refuel(0)` returns
true (this checks fuel-validity without consuming); `"marker"` -> name contains the resolved
marker name (see below). Returns the first matching slot or nil.

Marker item resolution (once, at startup, before the main loop): if `MARKER_MATCH` is set,
the marker name is that string. If nil, scan slots 1-16 for the first stack that is none of
bridge/sign/fuel, and pin its exact item name as the marker name for the rest of this run
(do not re-derive per-placement — re-picking "the first non-X stack" mid-run could jump to a
different item as inventory shifts). Print "Using <name> as the marker block." once resolved,
or a note that none was found if no such stack exists (markers/signs will simply report
"none in inventory" the first time one is needed, and the turtle returns home — this is
expected, not an error).

=== FUEL ===
`refuelIfNeeded()`: if `turtle.getFuelLevel() == "unlimited"`, always succeed, no checks. Else
while fuel < `FUEL_LOW`: `findSlot("fuel")`; if found, `turtle.select(slot)` then
`turtle.refuel(1)` (one item at a time) until fuel >= `FUEL_TARGET` or no more fuel is found.
Before each column in the main loop: call `refuelIfNeeded()`, then if
`turtle.getFuelLevel() ~= "unlimited"` and fuel < `dist + FUEL_MARGIN`, trigger the fuel
return-home reason (use the literal current `dist`, not `dist+1` — this is the locked rule).

=== BIOME READ ===
`readBiome()`: get the detector via `peripheral.find("environmentDetector") or
peripheral.find("environment_detector")` (resolved once at startup — see Startup gate below).
Call its `getBiome()`; normalize the result: a string is used as-is; a table uses
`.name`, else `.id`, else `[1]`, whichever is present; anything else means "couldn't read
this time" — print a short note and skip the marker check for this column only (not a return
trigger; try again next column).

=== SIGN TEXT ===
`prettifyBiome(id)`: strip the mod namespace before the colon, split the remainder on `_`,
capitalize each word, join with spaces (`"minecraft:dark_forest"` -> `"Dark Forest"`,
`"blue_skies:x_y"` -> `"X Y"`). `wrapSignText(name, dist)`: greedy word-wrap `name` into lines
of at most 15 characters, capped at 4 lines total; if the wrapped name used 3 lines or fewer,
append one more line reading `"<dist>m out"` using the column's `dist` at the time of
marking. Join all lines with `"\n"` — this is the exact string passed to `placeDown(text)`
for the sign (CC:Tweaked writes it onto the sign being placed, `\n` separates lines).

=== BIOME MARKER SEQUENCE ===
Read the biome once per column, comparing to `state.lastBiome` (`nil` counts as different, so
the very first column always checks). If it differs: attempt the marker sequence below. On
success, set `state.lastBiome` to the new biome and continue. If a marker or sign is needed
but not carried, do NOT update `lastBiome` — instead stop the loop right here (do not advance
past this column) and go home reporting "Out of signs." or "Out of marker blocks." (whichever
was missing) so the same biome gets marked on the next run once refilled.

Placement timing relative to `WIDTH` (CONTEXT.md specifies the sequence assuming the turtle
is already "over the edge lane, facing out"; it does not say how that interacts with
`WIDTH > 1` lane placement, since the design's worked example is `WIDTH = 1` throughout —
this is a deliberate, documented interpretation, not a narrowing of scope): run the check
immediately upon finishing the MARKER_SIDE's outermost lane placement within the per-column
loop below, before any further lane placement happens — for `MARKER_SIDE == "left"`, that's
right after lane 0 is placed, before sidestepping out to build lanes 1..WIDTH-1; for
`MARKER_SIDE == "right"`, that's right after the last lane (`WIDTH-1`) is placed, before
returning to lane 0. At `WIDTH = 1` (the default) both edges are lane 0 and this collapses to
the simple, fully-specified case.

Sequence, turtle at deck+1 over the edge lane, facing `"out"` (all raw calls — do NOT touch
`state.lane`/`state.dist`; the sequence is symmetric and returns to the exact start
cell/heading by construction, so nothing needs bookkeeping mid-sequence):
1. `turnR()` or `turnL()` toward `MARKER_SIDE` (one call).
2. `forward()`-style obstacle-clear-then-move, one block (reuse the dig/attack/give-up loop,
   just not the position-tracking wrapper).
3. `turtle.inspectDown()`: if air/liquid, `turtle.select(findSlot("marker"))` and
   `turtle.placeDown()`; if it fails because no marker slot exists, this is the "out of
   marker blocks" case — abort the sequence (do not proceed to steps 4-9) and report as
   above. If a solid block is already there, use it as-is (no placement, no consumption).
4. `turtle.up()` (clear-if-blocked, rare).
5. `turtle.inspectDown()`: if empty, `turtle.select(findSlot("sign"))` and
   `turtle.placeDown(wrapSignText(prettifyBiome(biome), dist))`; if no sign slot exists, this
   is the "out of signs" case — abort here (marker already placed/found is fine to leave; do
   not undo it) and report as above. If NOT empty (a sign is already there from a previous
   run), skip placing — treat as already handled.
6. Raw 180-degree turn (`turnR()` twice, or `turnL()` twice — either is fine since it's a
   full reversal).
7. `forward()`-style obstacle-clear-then-move, one block, back over the edge lane.
8. `turtle.down()` (clear-if-blocked, rare).
9. One `turnR()` or `turnL()` (whichever undoes step 1) to finish facing `"out"` again.
On success, increment `state.signs` only when a NEW sign was actually placed (not when
skipped because one already existed), and increment nothing extra for the marker (it is not
separately counted).

=== COLUMN BUILDING (per column, at `dist+1`, the deck spot below the turtle) ===
`placeColumnPiece()`, called once per lane: `turtle.inspectDown()` — if the name contains
`BRIDGE_MATCH`, skip (already built, counts toward this column, keeps reruns idempotent,
does NOT increment `state.placed`); if air/water/lava, `turtle.select(findSlot("bridge"))`
then `turtle.placeDown()` and increment `state.placed`; if any other solid block, leave it
alone unless `REPLACE_TERRAIN`, in which case `turtle.digDown()` then place as above. Never
`digDown` otherwise. Bridge pieces take their horizontal facing from the turtle's heading at
`placeDown()` time, so only ever call this while `heading == "out"`.

Per-column sequence: (a) `placeColumnPiece()` at lane 0; if `MARKER_SIDE == "left"`, run the
biome/marker sequence now; (b) for each additional lane `1..WIDTH-1`: `turnR()`, `forward()`
(sidesteps one lane right, obstacle-clearing as usual), `turnL()` (back to facing `"out"`),
then `placeColumnPiece()` at this lane; if this is the last lane (`WIDTH-1`) and
`MARKER_SIDE == "right"`, run the biome/marker sequence now; (c) return to lane 0: `turnL()`,
`forward()` repeated `lane` times (each decrements `lane`), `turnR()`; (d) if the biome/marker
sequence aborted for missing inventory anywhere above, stop the whole build loop now (do not
advance) and go home with that reason; otherwise `forward()` once more (`heading == "out"`,
`dist += 1`) to reach the next column, and loop.

Top-of-loop return checks, before starting each new column (order: stop flag, out of pieces,
length limit, fuel):
1. `stopRequested` (Q was pressed) -> "Q pressed -- finishing this column, then heading
   home." (the flag is only ever checked here, between columns, which is what makes it wait
   for the in-progress column to finish).
2. `findSlot("bridge") == nil` -> "No bridge pieces left. Heading home."
3. `MAX_LENGTH > 0 and dist >= MAX_LENGTH` -> "Reached the length limit (" .. MAX_LENGTH ..
   " blocks). Heading home."
4. After `refuelIfNeeded()`, fuel still short per the Fuel section -> "Not enough fuel to get
   back (have " .. fuel .. ", need " .. (dist + FUEL_MARGIN) .. "). Heading home."
If any of these fire, print the reason and break out of the loop (do not start a column).

=== STARTUP GATE ===
Before entering the build loop (but after handling `reset`/`status`, which never reach this
point): resolve the environment detector via `peripheral.find("environmentDetector") or
peripheral.find("environment_detector")`. If neither exists, print "No Environment Detector
found. Equip an Advanced Peripherals Environment Detector on one side and try again." and
return without building or moving.

=== STARTUP / RESUME ===
No state file -> fresh state: `dist=0, lane=0, heading="out", built=0, lastBiome=nil,
placed=0, signs=0, fOut=nil`; read `homeBlock` from `turtle.inspectDown()` (warn — but
continue — if its name doesn't contain `"moonstone"`; if inspect fails entirely, warn "No
block detected below me -- expected the vitreous moonstone. Continuing anyway." and leave
`homeBlock = nil`, and later skip the home-name verification if it's nil). Reset
`placed`/`signs` to 0 at the top of every invocation regardless (they're per-run counters).

If `dist == 0` on load (at home, facing out — the script always leaves it that way):
`travelToFrontier()` — while `dist < built`: `forward()`, then `turtle.inspectDown()` on the
new column; if it is NOT a bridge piece and NOT solid (i.e. it's open/liquid) -> correct
`built = dist` and stop this fast-travel loop (the recorded frontier was stale). After the
loop (or immediately if `built == 0`), keep advancing with plain `forward()` calls for as
long as `turtle.inspectDown()` at the new column shows an existing bridge piece (someone
extended it by hand — bump `built = dist` each time this happens), stopping the moment the
deck below is not a bridge piece. The turtle is now positioned at exactly the next column
that needs building, and the main loop resumes there.

If `dist > 0` on load (rebooted mid-bridge — `heading` is unknown, a turtle can't sense
facing): probe recovery. If `findSlot("bridge")` is nil or `fOut` is nil, print "Put me back
on the moonstone facing the bridge and run `bridge reset`" and stop — do not attempt
anything else. Otherwise: `turtle.select(findSlot("bridge"))`, `turtle.placeUp()`,
`turtle.inspectUp()` to read `.state.facing` (a compass string), `turtle.digUp()` to remove
the probe piece. If the placement/inspect failed or `.state.facing` is nil, print the same
"put me back..." message and stop. Otherwise compute the ring index of both compass
directions in `{"north","east","south","west"}` (clockwise order — matches
`turtle.turnRight()`, which turns clockwise) and take `diff = (probedIndex - fOutIndex) mod
4`: `0 -> "out"`, `1 -> "right"`, `2 -> "back"`, `3 -> "left"`. Set `state.heading` to that
value, then `faceRel("out")` to physically turn there. If `state.lane > 0` after this, return
to lane 0 first using the same `turnL()`/`forward()` x`lane`/`turnR()` sequence as the
per-column loop's "return to lane 0" step. Then resume the main loop from the current `dist`.

Capture `fOut` the very first time a bridge piece is successfully placed anywhere in the
run's lifetime (i.e. only if it's still nil): read `turtle.inspectDown()` (or `inspectUp` for
the probe case) `.state.facing` right after that placement and store it — this only ever
needs to happen once, ever, across the state file's lifetime.

=== GOING HOME ===
Before turning back, set `state.built = state.dist` (record the frontier for next run) and
`saveState()`. Then `faceRel("back")`, `forward()` repeated `dist` times (decrementing `dist`
to 0 as it goes, using the same obstacle-clearing `forward()`), then `faceRel("out")` again
(so a refill + rerun needs no repositioning). At `dist == 0`, verify: `turtle.inspectDown()`
name equals `homeBlock` (skip this whole check if `homeBlock` is nil). If it matches, done.
If not: `forward()` once, check again; if it matches here, this is actually home — correct
`dist = 0` and stop. If still no match, go `back` two blocks from there (one block behind the
original assumed home) and check once more; if it matches, correct `dist = 0` and stop.
Otherwise `error("Lost track of home. Put me back on top of " .. homeBlock .. " and run
`bridge reset`.")`.

Final report line (after arriving home): `print(string.format("Placed %d piece(s) this run.
Bridge is %dm long, %d sign(s) placed this run. Refill and run again.", state.placed,
state.built, state.signs))`.

=== MAIN / CLI ===
`local args = { ... }`. `args[1] == "reset"`: delete `STATE_FILE` if it exists, print "Forgot
the saved bridge progress." and `return` (mirror `crater.lua reset` — exits, does not build).
`args[1] == "status"`: load state if present (else note "No saved state yet -- never run.")
and print every field, then `return` without moving or checking peripherals. Otherwise: load
or initialize state as above, run the startup gate, then wrap the main loop in a `run()`
function and a `keyWatcher()` (`os.pullEvent("key")`, `keys.q` sets `stopRequested = true` and
prints "Q pressed -- finishing this column, then heading home." exactly once), and drive them
with `print("Press Q to stop after the current column."); parallel.waitForAny(run,
keyWatcher); print("Stopped.")` — matching `crater.lua`'s ending exactly.

=== NON-GOALS (do not build) ===
No GPS, no multi-turtle coordination, no chest refilling, no turning corners. One file, no
speculative abstractions beyond what's specified above.
