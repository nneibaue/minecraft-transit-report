A placed `TransitChartBlock` gets a `TransitChartBlockEntity` + `TransitChartRenderer` that draws the bundled `sample-bodygraph.png` on its face: ~2 blocks wide, height computed dynamically from the image's real pixel dimensions, bottom-anchored, floating a small offset in front of the block's face, oriented per the block's `FACING` state, fully emissive (legible in total darkness), and never culled or popped while the anchor block is on screen or the player is within the default 64-block block-entity render distance.

## Corrections to 04-RESEARCH.md / 04-PATTERNS.md (verified 2026-09-08 via javap against this project's own cached `.gradle/loom-cache` Minecraft 1.20.1 official-mappings jars -- not assumption, not documentation)

04-RESEARCH.md and 04-PATTERNS.md contain several API names that do not exist, or exist under different names, in this project's actual compiled dependencies. Every item below was confirmed empirically (jar content listing + `javap -p -c`) against `minecraft-clientOnly-*.jar` / `minecraft-common-*.jar` in this repo's own `.gradle/loom-cache`, and against the `fabric-rendering-v1` module already on this project's classpath. Follow the corrected names below, not the research/pattern documents, for every item listed:

1. **`BlockEntity.getRenderBoundingBox()` does not exist anywhere in this codebase.** It is a Forge-only API from older Minecraft versions; grepping the full contents of both the client and common jars for `RenderBoundingBox` (any case) returns zero matches. Do NOT attempt to override it on `TransitChartBlockEntity` -- it will not compile as an `@Override`, and without `@Override` it silently does nothing. The real, verified mechanism for "this block entity's render extends past its own footprint and must not be culled/popped" is `BlockEntityRenderer.shouldRenderOffScreen(T)`, a default method returning `false` on the interface. `BeaconRenderer.shouldRenderOffScreen(BeaconBlockEntity)` (the beacon-beam renderer, which has the exact same problem -- visual content far exceeding the block's own AABB) overrides it to unconditionally `return true`, confirmed via bytecode inspection. `ChunkRenderDispatcher$RenderChunk$RebuildTask` confirmed to add any block entity whose `shouldRenderOffScreen()` returns true to a `globalBlockEntities` list, exempting it from per-chunk-section frustum culling. Override `shouldRenderOffScreen` on `TransitChartRenderer`, not any method on `TransitChartBlockEntity`.
2. **`BlockEntityRenderer.getViewDistance()` already defaults to 64** (`bipush 64; ireturn` in the interface's default method body). ROADMAP's REND-07 wording is "remains visible out to the *default* 64-block... distance" -- this is validating default behavior, not asking for an override. Do not override `getViewDistance()`.
3. **The emissive light constant is `net.minecraft.client.renderer.LightTexture.FULL_BRIGHT`**, not `LightmapTextureManager.MAX_LIGHT_COORDINATE`. `LightmapTextureManager` does not exist in this jar at all (it is the Yarn name); the real Mojmap class is `LightTexture` (confirmed: `net/minecraft/client/renderer/LightTexture.class` present, declares `public static final int FULL_BRIGHT`).
4. **`VertexConsumer`'s overlay method is `overlayCoords(int, int)` (and a chainable single-int default `overlayCoords(int)`), not `overlayCoordinates(...)`.** Confirmed via `javap -p` on `com.mojang.blaze3d.vertex.VertexConsumer`. Use `net.minecraft.client.renderer.texture.OverlayTexture.NO_OVERLAY` as the single-int argument (confirmed field exists).
5. **The chainable `vertex(...)`/`normal(...)` overloads take `org.joml.Matrix4f` / `org.joml.Matrix3f` directly, not a `PoseStack.Pose`.** `PoseStack.Pose` (returned by `matrices.last()`) exposes `.pose()` -> `Matrix4f` and `.normal()` -> `Matrix3f`; pass those, e.g. `vertexConsumer.vertex(matrices.last().pose(), x, y, z)` and `.normal(matrices.last().normal(), nx, ny, nz)`.
6. **The Fabric registration class is `net.fabricmc.fabric.api.client.rendering.v1.BlockEntityRendererRegistry`** (static method `register(BlockEntityType<E>, BlockEntityRendererProvider<? super E>)`), not `BlockEntityRenderers`. Confirmed present on this project's classpath via the already-resolved `fabric-rendering-v1` module under `.gradle/loom-cache/remapped_mods`.
7. **`Direction.get2DDataValue()` does NOT map NORTH->0, EAST->1, SOUTH->2, WEST->3** as 04-RESEARCH.md assumed (flagged there as `[ASSUMED]`). The real, bytecode-confirmed mapping is **SOUTH->0, WEST->1, NORTH->2, EAST->3**. Do not hand-roll `get2DDataValue() * 90` arithmetic at all -- use `Direction.toYRot()` instead (confirmed to exist, returns `(data2d & 3) * 90` as a float), which is the purpose-built, idiomatic vanilla API for exactly this conversion and sidesteps the mapping entirely.
8. **A directly-bound (non-block-model) texture `ResourceLocation` must include the full `textures/...` prefix and the `.png` suffix** -- e.g. vanilla's `PigRenderer` binds the literal string `"textures/entity/pig/pig_saddle.png"` (confirmed via bytecode). This differs from the block-model `TextureSlot` convention (which strips both) that 04-PATTERNS.md's example incorrectly carried over. The texture constant must be `JollyalchemyTransitReport.id("textures/block/transit_chart.png")`, WITH the `.png` extension.
9. **Rotation formula, confirmed against a real shipped analog.** `DecoratedPotRenderer` (a `BlockEntityRenderer` that rotates rendered content per a `Direction`, the closest real vanilla precedent to this task) does exactly: `matrices.translate(0.5, 0.0, 0.5); matrices.mulPose(Axis.YP.rotationDegrees(180.0f - direction.toYRot())); matrices.translate(-0.5, 0.0, -0.5);` -- confirmed via bytecode. The `180.0f` term is specific to how that renderer's own model is authored; for a quad authored (per this plan) to face south (+Z, normal `(0,0,1)`) at zero rotation, the equivalent base offset is `0`, giving `Axis.YP.rotationDegrees(-facing.toYRot())`. Use this as the implementation, but this sign is the one piece in this plan not independently re-derivable from bytecode alone (it depends on JOML's rotation handedness, which was not independently verified) -- confirm it against the real, asymmetric `sample-bodygraph.png` during Task 2's four-orientation visual pass (exactly the situation D-02's asymmetric-image choice exists for). If the chart's orientation is mirrored/backwards relative to `FACING` in that pass, flip the sign to `+facing.toYRot()` and re-verify -- do not guess further without the visual test.
