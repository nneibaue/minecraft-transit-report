<decisions>
## Implementation Decisions

### Tooltip Wording and Tone

- **D-01:** The item tooltip carries **two lines**: a plain functional line first, an italic flavor line second — matching vanilla's info-first, flavor-second convention (e.g. compass, clock).
  1. Functional line (plain): `Right-click to refresh.`
  2. Flavor line (italic): `What the sky is doing, right now.`

  The flavor line is time/transit-themed, echoing the recipe rationale's "Clock at center — the transit endpoint is parametrized by timestamp and nothing else" without repeating it literally. This is a deliberate choice over distance/echo-themed or divination/bodygraph-themed flavor — the user picked the time angle specifically.

  — **Reversibility:** reversible — both lines are translation-key values in the generated language JSON; changing the wording later is a one-line edit and a `runDatagen` re-run, no code changes.

- **D-02:** The tooltip line(s) come from **new translation keys generated by data generation** (GEN-05), following the exact same pattern already established in `TransitReportLanguageProvider` (`src/client/.../JollyalchemyTransitReportDataGenerator.java`) for the existing `block.jollyalchemy-transit-report.transit_chart` and `text.jollyalchemy-transit-report.refreshing` keys. The planner should pick appropriate key names (e.g. `item.jollyalchemy-transit-report.transit_chart.tooltip` and a second key for the flavor line, or a single multi-line value if the 1.20.1 tooltip API prefers that shape — confirm against resolved sources, not tutorials, same working practice as everywhere else in this project) and wire them into `TransitChartBlock`'s (or `TransitReportBlocks`' `BlockItem`) tooltip-append behavior.

  **Note:** the existing `text.jollyalchemy-transit-report.refreshing` key ("Refreshing transit chart...") already in the language provider is a *different* string, likely meant for a later phase's in-progress/loading state (not this phase's static tooltip) — do not confuse the two or reuse one for the other.

### Claude's Discretion

The user discussed only the Tooltip area. Everything else in this phase is either already locked in REQUIREMENTS.md (recipe ingredients, both active and commented-out thematic) and Phase 2's decisions (loot table drop behavior), or is a technical implementation detail with no user-facing gray area:

- **Recipe/loot table provider placement:** both the recipe provider and the loot table provider go into the same single `fabric-datagen` entrypoint class (`JollyalchemyTransitReportDataGenerator`, in `src/client`) via additional `pack.addProvider(...)` lines — following the exact pattern already used for the language and model providers. This project's `fabric.mod.json` declares only one `fabric-datagen` entrypoint (client-side), so there is no separate "common" data generator to place recipe/loot table providers into, even though those provider types are not conceptually client-only elsewhere in Fabric's API.
- **Recipe unlock criterion:** standard Fabric/vanilla practice is `.unlockedBy("has_dirt", has(Items.DIRT))` or equivalent — trivial since every player has dirt access essentially immediately. No user decision needed.
- **Loot table shape:** `dropping(TransitReportBlocks.TRANSIT_CHART)` (or equivalent 1-for-1 self-drop helper) via a `FabricBlockLootTableProvider` subclass, matching D-10's "no special tool required" default. No Silk Touch distinction, no explosion-survival special-casing requested.
- **FabricRecipeProvider method shape (MEDIUM confidence risk, carried from STATE.md/ROADMAP.md):** the exact 1.20.1 `FabricRecipeProvider` generation method signature should be confirmed against `./gradlew genSources` output or `javap` against the cached jar during execution — not against current Fabric documentation, which describes post-1.21 provider signatures. This is the same class of risk already flagged and resolved for Phase 2's model-provider shape.

## Existing Code Insights

### Reusable Assets
- `TransitReportBlocks.TRANSIT_CHART` (`src/main/java/transitreport/TransitReportBlocks.java`) — the registered `Block` instance the loot table and recipe providers both reference. `TRANSIT_CHART_ITEM` is the `BlockItem` the recipe output and the tooltip attach to.
- `JollyalchemyTransitReport.MOD_ID` / `JollyalchemyTransitReport.id(String path)` — use for every new `ResourceLocation` (recipe id, loot table id, translation keys), consistent with existing registration code.
- `JollyalchemyTransitReportDataGenerator` (`src/client/java/transitreport/client/JollyalchemyTransitReportDataGenerator.java`) — the single `fabric-datagen` entrypoint. `onInitializeDataGenerator` already calls `pack.addProvider(TransitReportLanguageProvider::new)` and `pack.addProvider(TransitChartModelProvider::new)`. This phase adds two more `pack.addProvider(...)` lines (recipe provider, loot table provider) and grows the existing `TransitReportLanguageProvider.generateTranslations` with the new tooltip keys.
- `TransitReportLanguageProvider` (private static nested class in the same file) — already has a working `generateTranslations` override with two entries (`text....refreshing`, `block....transit_chart`). D-01/D-02 add the tooltip key(s) here, following the identical `translationBuilder.add(...)` pattern.

### Established Patterns
- **Split source sets, single datagen entrypoint.** All datagen providers — regardless of whether they're conceptually "client-only" — live in the one `fabric-datagen` class in `src/client`, because that's the only entrypoint declared in `fabric.mod.json`. Recipe and loot table providers follow this same placement, not a new "common" datagen entrypoint.
- **Mojang official mappings**, not Yarn — `loom.officialMojangMappings()`. See CLAUDE.md §2. `FabricRecipeProvider`'s exact generation method name/signature on 1.20.1 needs confirming from resolved sources (flagged above).
- Verification is visual-only via the dev client (established in Phases 1 and 2, D-03/D-04/D-05 across those CONTEXT.md files) — no automated Minecraft-side test harness exists or is planned.

### Integration Points
- `src/client/java/transitreport/client/JollyalchemyTransitReportDataGenerator.java` — two new `pack.addProvider(...)` calls (recipe, loot table) and new entries in `TransitReportLanguageProvider.generateTranslations`.
- New: a `FabricRecipeProvider` subclass generating the active single-dirt shapeless recipe, with the thematic 3x3 recipe adjacent as commented-out code (GEN-06).
- New: a `FabricBlockLootTableProvider` subclass generating the block's self-drop loot table (GEN-04).
- Wherever 1.20.1 attaches item tooltips (`Item.appendHoverText` override on a custom `BlockItem` subclass, or equivalent) — needs confirming against resolved sources per the mappings risk above. If a custom `BlockItem` subclass is needed, `TransitReportBlocks.TRANSIT_CHART_ITEM`'s construction changes from `new BlockItem(...)` to the new subclass.
